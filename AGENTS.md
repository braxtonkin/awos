# Rules for autoworker-oss

These rules apply to every change in this repo, whether an agent or a person wrote it. [docs/spec.md](docs/spec.md) specifies the system these rules build. [docs/decisions.md](docs/decisions.md) records the settled design decisions and the options that lost. Do not reopen a settled decision without new evidence. Every rule has an ID. Cite IDs in reviews and commit messages, for example `move parser into its feature folder (A4)`.

## The rule behind the rules

When an agent makes a mistake, or when you are about to leave a review comment, fix the cause at the highest level that works:

1. **Architecture**: make the mistake impossible through types, data structures, or module boundaries.
2. **Static checks**: compiler, type checker, lint, CI. A violation must fail the build.
3. **Guidance**: this file, skills, AI review. Useful, but an agent can skip it.
4. **Human review**: the last resort. A review comment that keeps coming back points to something missing in levels 1 to 3.

Never fix a repeated mistake only by rewording a prompt. Most rules below are enforced by this file alone for now; the [enforcement table](#enforcement) tracks moving each one up to a check.

## A. Codebase design

- **A1. The codebase is the example.** Agents copy the patterns they see. Merge only code you would be happy to see copied everywhere.
- **A2. The shortest path is the correct path.** Agents take the quickest route. If the quick way to do something is wrong, change the codebase until the quick way is right.
- **A3. One paved path.** Each kind of thing (feature, command, config, test) has exactly one approved way to build it, recorded under [Paved paths](#paved-paths). Do not add a second way. If the paved path does not fit, change it in its own PR.
- **A4. A feature lives in one folder.** All code for a feature, including logic, interface, tests, and fixtures, lives in `features/<name>/`. Code moves to a shared module only when a second feature needs it.
- **A5. Boundaries are checked by machine.** Which modules may import which is declared in config and checked in CI, not left to convention.
- **A6. Design for the contributor with the least context.** A newcomer, a non-engineer, or a small model should be able to add a feature by copying an existing one. Accept constraints that feel heavy to humans; agents absorb the friction.
- **A7. Prefer strict tools.** Choose languages, compilers, and settings that turn mistakes into build errors, and enable their strictest modes.

## B. Keeping the codebase clean

- **B1. No code comments.** Names, types, and structure carry meaning. If code needs a comment to be understood, restructure it. If it is a workaround, fix the cause or open an issue. Agents write comments that go stale and treat workaround comments as permission to repeat the workaround. The only exceptions are lines a tool needs in order to run, such as a shebang.
- **B2. No suppression directives.** No `eslint-disable`, `@ts-ignore`, `noqa`, `#[allow]`, or similar. If a check is wrong, change its config in its own PR.
- **B3. No quiet workarounds.** One merged workaround becomes the pattern within days. Fix the cause, or record it as an issue and stop.
- **B4. Stop the bleeding first.** When you find a bad pattern, first add a check that blocks new instances, then remove the existing ones in follow-up PRs.
- **B5. Delete freely.** Remove dead code, unused exports, and stale docs when you find them.
- **B6. Growth is a reviewed decision.** The codebase grows only within the ceilings in `budget/budget.json`, and a ceiling goes up only in a commit that changes nothing outside `budget/`, so a reviewer sees each growth decision on its own. A ceiling can go down in any commit.

## C. Verification

- **C1. Agents verify their own work.** Every change is run for real: the app, the CLI, the service. Report the exact commands you ran and what you observed. "Should work" is not verification.
- **C2. One verification tool.** Verification lives in a checked-in tool that agents extend. Do not write throwaway scripts each session.
- **C3. Keep the feature map current.** [docs/feature-map.md](docs/feature-map.md) lists every user-facing feature: what it does, how to reach it, and where its code lives. Update it in the same PR as the feature.
- **C4. Correct is not the same as good.** Verification proves a change works. Quality comes from sections A and B.
- **C5. Model concurrent protocols before building them.** Code that coordinates concurrent actors, such as claims and leases, the stage machine, the outbox, or event delivery, gets a TLA+ model before the code is written. The model runs in CI whenever it or the code it covers changes, and the verification skill says how to run it.
- **C6. Put invariants in structure and check behavior by simulation.** Put each invariant where the build or the store enforces it, in a type, a schema constraint, or a TLA+ property, and prove it can fail with a negative control, such as a planted violation or a mutant. Check behavior by running the real code in a seeded simulation that injects faults and checks those invariants after every step. Write a unit test only for a pure function whose logic a simulation cannot reach, and never one that restates the code.

## D. Adding a feature

- **D1. Copy the closest example.** Find the most similar existing feature and follow its shape.
- **D2. Reproduce before fixing.** For a bug, show the failure with the verification tool before changing code.
- **D3. Do not guess.** Read the code the change touches. If you cannot find evidence for a claim, say so.
- **D4. Small, atomic PRs.** One idea per PR, so history stays readable and reverts stay cheap. Split large changes.
- **D5. Finish the whole change.** Tests, the feature map, and paved-path docs are updated in the same PR as the code.

## E. Working with agents

- **E1. Repeated corrections become checks.** If you correct an agent for the same thing twice, apply the ladder above.
- **E2. Skills come from observed failures.** Write or change an agent skill only after watching an agent fail at something specific. Test the change with an eval before relying on it.
- **E3. Autonomy is earned in steps.** Watched local agents come first, then background or cloud agents, then auto-merge. Move up a step only when verification (C1, C2) and the checks in the enforcement table are in place.

## Stack

Each tool below is the only approved tool for its job (A3). To replace one, or to add a second tool for the same job, change this list in its own PR.

- **Language.** TypeScript on Node 24 LTS, with `strict`, `noUncheckedIndexedAccess`, and `exactOptionalPropertyTypes` on.
- **Lint.** ESLint with typescript-eslint `strictTypeChecked`, typed from the root tsconfig, from one config at the repository root, run only through `npm run lint`.
- **Boundaries.** dependency-cruiser, from `.dependency-cruiser.json`, run only through `npm run boundaries`.
- **Database.** Postgres. The schema lives in plain SQL migrations that `dbmate` runs. Invariants are schema constraints.
- **Queries.** Kysely, with types that `kysely-codegen` generates from the database. No ORM.
- **Outside data.** zod parses every payload, file, and environment variable where it enters.
- **Secrets.** The app encrypts secrets with AES-256-GCM from `node:crypto` before they reach Postgres. The key comes from a Kubernetes Secret and never reaches the database.
- **Tests.** Vitest against a real Postgres that Testcontainers starts. No database mocks.
- **Formal models.** TLA+, checked with TLC from `tla2tools.jar` v1.7.4 on Java 21, both pinned in the verify image. A model lives in the feature folder of the code it covers (A4).
- **Dashboard.** Next.js App Router. Server components read Postgres, and server actions write to it.
- **Connectors.** Octokit for GitHub. `fetch` and zod for Jira and Webex.
- **Agent runtime.** The Codex app server (`codex app-server`), pinned to one exact Codex CLI version and run inside each attempt's Job. Use only the protocol's stable methods.
- **Browser.** `playwright-core` at one exact version drives the Chromium headless shell that release pins, only from the verify tool. The verify image installs that build and its FFmpeg from Playwright's download host, each pinned by checksum.
- **Deployment.** Kubernetes.
- **Kubernetes API.** `@kubernetes/client-node` 1.4.0, the release whose types fit `@types/node` 24, with `@types/ws` for the `ws` types it leaves out. Local clusters come from kind v0.33.0, pinned in the verify image for amd64 hosts.

## Paved paths

The first feature, command, or module of each kind defines its paved path. Record it here in the same PR.

- **Layout.** Feature code lives in `features/<name>/`. Entry points live in `services/engine/`, `services/dashboard/`, and `services/job/`, and hold no logic. Each folder directly under `features/` or `services/` is named with lowercase letters, digits, and dashes, and starts with a letter. Code moves to `shared/` only when a second feature needs it. Migrations live in `db/migrations/`, each under a version prefix no other migration uses, which `npm run migration-versions` checks, and tools live in `tools/`.
- **TypeScript.** Node 24 runs `.ts` files directly, so there is no build step. Import with the `.ts` extension, use `import type` for types, and write only syntax Node can erase, so no `enum` and no `namespace`. `npm run check` runs `npm run shape`, `npm run sql-comments`, `npm run migration-versions`, `npm run model-names`, `npm run step-names`, `npm run strict-schemas`, `npm run ci-plan`, `npm run budget`, `npm run typecheck`, `npm run lint`, `npm run boundaries`, then `npm run db-types`. `npm run lint` lints against the root ESLint config and the root tsconfig, so a nested config of either kind changes nothing.
- **Verification.** `npm run verify -- <scenario>` runs one scenario, prints `PASS` or `FAIL` per check, and exits non-zero on any failure. A feature's scenarios live in `features/<name>/verify.ts`, which exports `scenarios`. Run everything inside the verify container, which CI uses too. Install with `docker compose run --rm verify npm ci`, again after any change to the lockfile, then run `docker compose run --rm verify npm run verify -- <scenario>`. A live lane, one that reaches the cluster, Jira, GitHub, or Codex, runs in the `live` service instead. `live` runs the verify image with the same mounts. It loads `~/.autoworker/sandbox.env`, which sets `JIRA_SITE`, `JIRA_EMAIL`, `JIRA_API_TOKEN`, and `GITHUB_TOKEN` one unquoted `KEY=value` per line, into its environment when that file exists. It mounts `~/.autoworker/codex/` read-only at `/codex`, where an access-only Codex login sits as `auth.json`. `npm run verify -- accounts` checks the four keys, the Jira and GitHub tokens, and that no mounted login holds a refresh token, and it prints no value. Never run `docker compose config`, print a `live` container's environment, or copy a compose error about the sandbox file into a transcript, because each can show the sandbox values. A lane that uses the cluster runs `npm run verify -- kind up` first in its own container, as in `docker compose run --rm live sh -c 'npm run verify -- kind up && npm run verify -- <scenario>'`, because the container's place on the `kind` network and the kubeconfig that `kind up` writes to `~/.kube/config` last only as long as the container. `kind up` creates the `autoworker` cluster that `tools/verify/kind.yaml` pins, or reuses it when its node runs the pinned image. Every worktree on the machine shares that cluster, so `kind up` never deletes a running one and recreates only a stopped one. `kind down` deletes it for everyone, so run it only when no other lane uses it. While GitHub Actions is disabled, CI runs on this machine: run `node tools/ci-local/main.ts` from the root of a clean worktree on the head you are about to integrate, and integrate only when its summary says `PASS`. It prints the head SHA, reads every `run:` step of `.github/workflows/ci.yml`, runs `docker compose build verify` and `docker compose run --rm verify npm ci` once, then runs the jobs at the same time, as GitHub does, with each job's steps in order through `docker compose run --rm -T verify`, and never stops early. It prints each result in `ci.yml` order, named for its job, and the summary ends with the wall time. Jobs share nothing a step writes: each step runs in its own one-off container, whose `/tmp` holds the guardrails copies and TLC's `-metadir`, and each job's Postgres gets its own container, password, and network alias. It writes one log per step and `summary.txt`, with each step's exit code and seconds, to `ci-local/<sha>/`, which git ignores, and exits non-zero when any step fails. It refuses a worktree with uncommitted changes. A run records its pid, SHA, start time, compose project, and run id in `ci-local/run.json`, and labels each step container with its run id. A second run in the same worktree is refused while the recorded pid is alive. A run that finds a record whose pid is dead first removes the step containers that dead run left, with the Postgres containers they own, and says so. Stop a run only with `node tools/ci-local/main.ts --stop` from its own worktree. It asks the recorded run to stop, and that run removes its own containers by the compose project and run labels, writes a `STOPPED` summary, and exits. Never stop a run with `Stop-Process`, `kill`, or `taskkill`: every run has the same command line, so a process list can't tell whose run it is, and a killed run leaves its step containers behind. Add a CI step to `ci.yml` and nowhere else. `npm run ci-plan`, which `npm run check` chains, prints the steps it would run and fails on a step it cannot run, such as a `uses:` action other than `actions/checkout` or a `run:` that is not `docker compose build verify` or `docker compose run --rm verify` followed by plain words.
- **Guardrails.** Every check that enforces a rule gets a case in `tools/verify/guardrails.ts`. The case plants a violation in a copy of the repository and passes only when the check rejects it. A plant is a new file, or an edit that replaces one exact string in a file the copy already holds and is undone after the case, so a check that reads real code, such as `strict-schemas`, is proved on that code. An exception the check allows gets an allowance case that plants the allowed line and passes only when the check accepts it, beside cases that prove the exception allows nothing more. Each check is an npm script, and a case runs that same script, so it proves the check CI runs. For each script that `npm run check` chains, one case runs `npm run check` itself, so a script dropped from the chain fails too. The case for `npm run verify -- models` runs in a copy without `features/`, so its plant is the only model and the guardrails never rerun the real models.
- **Checks.** A check that no tool in [Stack](#stack) can express is our own script at `tools/<name>/main.ts`, run as `npm run <name>` and chained into `npm run check`. It prints one line per violation, starting with the path it rejects, and exits 1 when there is any. It adds no tool, so Stack does not list it. A check that only reads files runs before `npm run typecheck`. A check that starts a container, such as `npm run db-types`, runs last, so the fast checks fail first. A check that reads product code parses it as text and never imports it statically, because `tools/` imports no product code. `npm run model-names`, for example, parses `invariants.ts` with the TypeScript compiler API. `npm run budget` counts files by the globs in `budget/budget.json`, never by path rules of its own, so a fork changes its roles there. A check that needs a value only running code produces, as `npm run strict-schemas` needs the JSON Schema each step sends, loads the module by a computed import and parses what it loads with zod. `tools/shape/` is the example.
- **Boundaries.** `.dependency-cruiser.json` declares them, and `npm run boundaries` enforces them as part of `npm run check`. The rules read static imports and re-exports. Imports only point down: `services/` may import `features/` and `shared/`, `features/` may import `shared/`, and `shared/` imports neither. Features never import each other, and no service imports another. `services/` and `shared/` never import `tools/`, because they deploy and must not pull in verification tooling. The rule is `product-code-imports-no-tools`. Features may import `tools/verify/`, which holds the verify scenarios' shared helpers and the Postgres harness, `tools/verify/postgres.ts`. Neither `tools/` nor a file outside a feature folder, a service folder, `shared/`, or `tools/` imports product code by a static import, so neither can carry one module to another. The verify tool loads each `features/<name>/verify.ts` by a computed import, which the rules do not see. `npm run shape` runs `tools/shape/main.ts` as part of `npm run check`. It rejects every symbolic link, so the rules and lint see each file at its real path. It rejects a `node_modules` folder below the root, because the rules and lint skip the code inside one. Agent tooling under `.claude/` may install its own packages. It also rejects any folder directly under `features/` or `services/` whose name does not match `^[a-z][a-z0-9-]*$`, because the rules put that name into a pattern, and any config that turns on `skipLibCheck`, as the Package types path says. It reads the files on disk, ignored ones included, and skips the root `.git` and `node_modules`. So a link that npm makes in the root `node_modules` for a `file:` dependency or a workspace still gets past it. Code in `services/job/` never imports a Postgres client, `kysely`, `shared/db/`, or a `@kubernetes` package, even through a helper. No import rule can see `fetch`, a raw socket, or a module loaded by a computed name, so the Job's pod spec stays its runtime boundary. No import is circular or orphaned.
- **Migrations.** A migration is `db/migrations/<YYYYMMDDHHMMSS>_<name>.sql`, plain SQL that dbmate runs. Write its `-- migrate:down` part to undo exactly what its `-- migrate:up` part does. `npm run verify -- migrations` proves it in CI. It applies the migrations one at a time, then rolls them back one at a time, and after each rollback it requires the schema to match what it was before that migration applied. Last, it applies them all again. A migration holds no comment except those two marker lines, each alone or followed by dbmate's `transaction:false` option, and no `COMMENT ON`, which kysely-codegen would copy into the generated types. `npm run sql-comments` rejects both, inside a dollar-quoted function body too. Name every check, unique constraint, foreign key, index, and trigger for the rule it enforces. Also name a not-null that a guard relies on, such as `attempt_runs_as_a_person`, and the not-nulls under the MATCH SIMPLE foreign key `live_attempt_matches_ready_task`, which skips a row that holds a null in any of its columns. Other not-nulls and primary keys keep the names Postgres gives them, and the simulator's catalog check skips those default names. No column defaults to `now()`. A statement that reads or writes a time takes it as a `Date` parameter, so the simulator can run it on a virtual clock. `shared/db/types.ts` is generated from the migrated schema and never edited by hand. Run `npm run db:types` in the same PR as the migration to regenerate it. Resolve a merge conflict in `shared/db/types.ts` the same way, by running `npm run db:types`, never by a hand merge. `npm run db-types` runs last in `npm run check` and fails when the file differs from a fresh generation. `db/migrations/20260923220000_tasks.sql` is the example.
- **Queries.** Product code reaches Postgres only through Kysely. Open a client with `connect(url, connections)` from `shared/db/client.ts`, and take the URL from the engine's settings, which parse `DATABASE_URL` with zod. Build each statement with Kysely's query builder. Use its `sql` template only for a statement the builder cannot express. When Postgres may refuse a statement, catch the error and pass it to `refusal()` from `shared/db/client.ts`. It returns the kind and the name of the constraint or trigger that refused the statement, or the table and column of a refused not-null, and `undefined` for any other error. Map each refusal the statement expects to a value of your own, and rethrow any other error. A test or a verify scenario starts Postgres with `withPostgres` from `tools/verify/postgres.ts`. That harness lives in `tools/`, not in `shared/`, because `shared/` deploys. `features/tasks/claim.ts` is the example.
- **Secrets.** A person's credential reaches Postgres only through `replace` in `features/credentials/store.ts`. It reads the secret with its connector kind's reader in `features/credentials/kinds.ts`, seals it with `features/credentials/seal.ts`, and calls `replace_credential`, a `security definer` SQL function that records the replacement as a `human_action` and writes the credential in one statement. `seal.ts` uses AES-256-GCM from `node:crypto` with a fresh 12-byte nonce per seal and the credential's connector and owner as additional data, so a sealed value moved into another row fails to open. The key version is stored beside the ciphertext. A service reads its key once at startup with `sealingKey(process.env)`. It parses `CREDENTIAL_KEY`, base64 of exactly 32 bytes such as the output of `openssl rand -base64 32`, and `CREDENTIAL_KEY_VERSION`, a positive whole number. `SealingKey` carries a brand that only `sealingKey` adds, so an object literal cannot pass for a key. The key comes from a Kubernetes Secret and never reaches Postgres, a log, or an error message. The engine reads a credential with `open`, which names each failure: no credential, another key version, or a failed GCM check. On success it also returns the `action_id` of the replacement it read, so a later write can require that nobody replaced the credential since. The `dashboard` role can select every `credential` column except `ciphertext` and can execute `replace_credential`. It cannot insert or update a credential or a `human_action` itself, so every write it makes is recorded. The dashboard service connects as a login role that is a member of `dashboard`. Roles belong to the whole Postgres cluster, so one cluster holds one AutoWorker database, and the user that runs migrations needs `CREATEROLE`. A replacement carries the action id its caller made, so a replayed id writes nothing, and a replay of a write that still stands returns that write. A Codex login that holds a refresh token is stored only when its caller says it was made for AutoWorker, because the engine's refresh signs out every other copy of that login. Postgres cannot use an enum value in the transaction that adds it. So a new connector kind adds its value to `connector_kind` in a migration of its own, as `db/migrations/20260923232000_credential_kinds.sql` does for `human_action_kind`, and then its row to `connector` in a later migration and its reader to `kinds.ts`, which `npm run typecheck` then requires. `npm run verify -- credentials` proves the store. `npm run verify -- credentials --mutant all` proves that each named guard and each missing privilege can fail. `npm test` runs both through `features/credentials/store.test.ts`, so CI enforces them. `features/credentials/` is the example.
- **Admin commands.** An admin command is a file in `services/engine/` that an admin runs with `node`, such as `node services/engine/setup.ts <file>`. It parses all of its input with zod before it writes anything, and it hands each part to the feature that owns it, which exports the part's schema and the function that applies it. It never prints a secret. Its input names each secret by an environment variable or a file path and never holds one, a zod message names the field and never the value, and a secret reaches Postgres only through `replace` in `features/credentials/store.ts`. It is idempotent: it matches each record by a natural key, writes only what differs, applies each section in one transaction, and prints one count per section. Its verify scenario runs it as a child process against a fresh database with made-up secrets, and checks that no output holds one. `services/engine/setup.ts` is the example.
- **Credential checks.** Each connector kind brings its own check. `checksFor` in `features/credentials/checks.ts` returns a record typed over `ConnectorKind`, so a kind without a check fails `npm run typecheck`. A check takes the opened secret and returns `valid`, `invalid`, or `unknown` with a cause, the expiry it learned, and its `refresh`: `unused` only when it proved it never presented a refresh token, `rotated` with the new secret, and `maybe-used` otherwise. The Codex check reports `unused` only when Codex exited on its own and left `auth.json` unchanged, so a run killed at its timeout keeps the login's refresh claim. Its `rotates` says whether it may use a refresh token. The engine's `checks` loop in `features/credentials/check-loop.ts` claims a check with one `insert ... select` into `credential_check` that runs only while the credential still holds the replacement and expiry the check opened and is still due, after it locks the credential row, and `finish` locks the same row first, so a pass that listed a credential before another check finished it skips it. The partial unique index `one_live_check_per_credential` lets one check run per credential, and `one_refresh_per_login` lets only one check ever try to refresh a given login, because a refresh token works once. When such a check loses its lease, the next check records the login `invalid` instead of refreshing it again. The trigger `finished_check_is_final` refuses any change to a finished check, so a checker that outlives its lease records nothing, and the trigger `stored_login_is_newest` refuses an earlier expiry under the same replacement. A rotated login goes back through `writeBack` in `features/credentials/store.ts`, which writes only over the login the check opened, with the same replacement and expiry, and only when the new expiry is later. The loop checks a credential after each replacement, and a Codex login once more inside its 5-minute refresh window, where an `unknown` verdict is retried until one check reaches a verdict or `triesInWindow` checks have run, and never more often, because one Codex check sends about 13,500 input tokens. `Pass` carries the engine's stop signal, and the loop checks it between credentials. The engine refuses a `CHECK_LEASE_MS` that is not more than `CHECK_TIMEOUT_MS` plus `checkLeaseMarginMs`. `loginForJob` takes the Job's time limit, refuses a login that expires before then as `expires-too-soon`, checks a login first when its last check is older than 6 hours, and gives a Job only an `AccessOnlyLogin`. Only `accessOnly` in `features/credentials/kinds.ts` makes one, by blanking the refresh token, so only the engine ever refreshes. `autoworker/no-brand-assertions` in `tools/eslint/no-brand-assertions.ts` rejects a type assertion or type predicate that adds a brand, which it finds by type as a property keyed by a unique symbol, so no code can mint an `AccessOnlyLogin`, a `SealingKey`, or any other brand except through the function that owns it. The Codex check runs `codex exec` on `gpt-6-luna` in a private temporary Codex home that it deletes on every path. `features/credentials/Checks.tla` models the protocol. `npm run verify -- credentials-sim` runs the real loop with several checkers against a fake issuer that refuses a reused refresh token, kills a Codex run after it presented the token, stalls a checker past its lease, and lets a pass act on a stale list, and `--mutant all` proves each guard. To add a kind, add its check file, its entry in `checksFor`, and its fake in `features/credentials/simulate.ts`. `features/credentials/codex-check.ts` is the example.
- **Package types.** When a package's own type declarations name a type that no installed package declares, `npm run typecheck` fails. Declare the missing names in `shared/types/<package>.d.ts`, named for the package whose declarations name them, one file per package, and never turn on `skipLibCheck`. For example, vitest depends on tinybench, whose declarations name `DOMHighResTimeStamp`, so `shared/types/tinybench.d.ts` declares it. A package that ships no types and has no approved `@types` package, such as `pg`, gets the same kind of file, which declares only the part of its API the code calls. Each file must be needed, so deleting it brings back a `tsc` error. Delete the file once the package declares what was missing. The sandbox repository that the end-to-end test seeds has no `shared/`, so `sandboxSeed` in `features/e2e/sandbox-seed.ts` writes each file its packages need into the seed under `types/`, copied from `shared/types/`, and the sandbox's tsconfig includes `types/`. This repository keeps one copy, and the root typecheck never sees two. `npm run shape` rejects any `.json`, `.yml`, or `.yaml` file that names `skipLibCheck` in any case, and any tsconfig that inherits it through `extends`. It exempts agent tooling under `.claude/` at the root.
- **Agent steps.** An agent step is `step({ runBy: 'agent', ... })` in its workflow's folder. Its core prompt is `features/<workflow>/prompts/<step>.md`, which states the step's input, its review, and where to stop, and grows only from failures seen in runs (E2). Its review is the step's zod `output`, which the engine sends as Codex's `outputSchema` through `outputSchema` in `shared/workflow.ts`, and `npm run strict-schemas` fails the build when that schema is not strict-compatible. It names the review blocks it `requires`. The workflow's `AgentSteps` plug from `shared/agent-step.ts` gives each step's input, settles its reply into the output and evidence, and names the actions each verdict owes, typed by the kinds the step declares in `owes`. `services/engine/main.ts` maps each workflow to its plug. `features/code-change/stage-output.ts` is the example. The worker and step runner in `features/tasks/` never name a step.
- **Formal models.** A model is `features/<name>/<Model>.tla` with `<Model>.cfg`, written before the code it covers. Give each guard in the design a boolean constant that the real config sets to `TRUE`. The feature's `verify.ts` declares the model through `defineModel` in `tools/verify/models.ts`. The declaration names the module, the real config as `pr` and the nightly config as `nightly`, each with a floor for each bound, the guards, each property with its section, the liveness properties, and each mutant with its guard, the property it must break, an optional `without` that says what dropping the guard allows, optional `overrides` of bounds or declared `settings`, and an optional trace shape. `defineModel` returns the `<name>-model` scenario, which runs TLC on the real config, then once per mutant with that mutant's guard set to `FALSE` and only its property checked. The scenario passes only when the real config holds and every mutant fails. Safety and liveness run as separate TLC runs. The run that shows the real config holds checks its liveness properties once, at the end, and a liveness mutant checks them as it goes, so it stops at the first violation. It first parses the config strictly: `TypeOK` and each invariant sit under `INVARIANTS` and each action or liveness property under `PROPERTIES`, a liveness property filed under `INVARIANTS` is refused by name, and the declaration's type refuses one declared under `INVARIANTS`, each constant is assigned once with `=` or `<-`, a mutant overrides only a constant the config assigns and never a guard, no line holds a comment, every guard is `TRUE`, every property and every guard keeps at least one mutant, and each bound is at or above its floor. So demoting an invariant, shrinking the model, hiding a value behind a comment, or dropping the last mutant of a property or guard fails too. A check of planted configs proves the parser still rejects each of these. Larger bounds go in `<Model>.nightly.cfg`. Every run of the scenario reviews it, and the scenario model-checks it in place of `<Model>.cfg` when it is given `nightly`, so a nightly config that fails its review fails the PR. `npm run verify -- models` runs every scenario whose name ends in `-model` and passes on the arguments that follow `models`. The `models` job in CI runs it on every PR. The nightly workflow, which runs only when someone starts it by hand, runs `npm run verify -- models nightly`, so a new model needs no workflow edit. Start it with `gh workflow run nightly.yml` before merging a batch into `main`, and after changing a nightly config. `npm run verify -- <name>-model --mutant <guard>` reviews the real config and runs only that guard's mutants. Each mutant's check prints its whole trace. `defineModel` is the only way to write a model, and `features/tasks/` is the example of a model and its configs.
- **End-to-end test.** The sandbox, a small TypeScript library with its own lockfile, lives in `features/e2e/sandbox/`. Each run branch, `e2e/run-<id>`, holds that folder and the package type files it needs, which `sandboxSeed` in `features/e2e/sandbox-seed.ts` adds, in a commit with no parent, so main never changes. Its workflow defines one job, `sandbox`, which is the context ruleset 23901469 requires on `e2e/run-*`. The test runs in the `live` service, which loads the sandbox tokens and the read-only Codex login: `docker compose run --rm live npm run verify -- e2e --driver <name>`. A driver plays AutoWorker's part and lives in `features/e2e/driver.ts`. Each frontier step lives in `features/e2e/frontier.ts` and observes the system that owns it, never the driver. Every Jira and GitHub payload passes through `parsePayload` in `features/e2e/payload.ts`, and each schema gets a plant in `e2e-payload`. A new catalog entry is one item in `features/e2e/catalog.ts`, with an acceptance test the agent never sees.
- **Review step.** When a pull request needs an approval, Land asks one `ReviewStep` from `features/code-change/land.ts` what to owe and what note the waiting task shows. `services/engine/main.ts` passes it in, so a fork swaps it there without editing the core. The core's step, `coreReview`, owes nothing and only names the pull request in its note, because approval comes from the repository's rules and a fork's plug-in. The core never approves and never requests a review. A step builds each action with `reviewOwes`, whose type accepts only the kinds that `ReviewKind` in `land.ts` lists, `ticket.comment` and `ticket.transition`. A plain `owe` result lacks the brand a step's actions need. So a step that approves, merges, or owes any other kind fails `npm run typecheck`. To let a review step owe a new kind, add it to `ReviewKind` in its own PR. The guardrail cases for the review step prove the list refuses `pr.merge` and an approval, and accepts a ticket comment.
- **Simulation.** A feature whose code coordinates concurrent actors runs that code in a seeded simulation, which checks the model's properties after every step (C6). `features/<name>/invariants.ts` exports `properties`, one object literal keyed by the model's property names, with any check the model does not state beside them. Each entry holds a predicate, a Kysely `sql` template that returns the rows that break the property, and a plant, SQL that breaks the property in a scratch database. In `features/tasks/`, `LiveAttemptWorksTheTaskStep`, `TaskHasItsRepository`, `ApproveNamesTheWaitingReview`, `SendBackCarriesItsNote`, `ActionHasOneTarget`, and `ActionTargetFitsItsKind` are checks that the model does not state. `provePlants` runs each plant in its own scratch database and passes only when the plant's property is reported, so every predicate is shown able to fail. `npm run model-names` fails when a model config lists a name that is not a key of `properties`, `TypeOK` included. It skips a feature whose folder, subfolders included, holds no `.ts`, `.tsx`, `.mts`, or `.cts` file other than its top-level `verify.ts`, because that model landed before its code (C5). It checks the feature once any other such file arrives. `simulate.ts` drives seeded workers on a virtual clock, injects faults, and runs every predicate after each step. `check_step`, the SQL function that runs them, finds the rows a step wrote by their xmin, and xmin identifies those rows only while no other transaction is open. So `check_step` waits up to a second for an older client transaction to end, then raises an error if one is still open. It ignores autovacuum, which can briefly hold a transaction id. Every statement takes the time as a parameter, so a seed replays exactly, except after a `race` move, which runs an attempt's finish, a person action, and two claims on one task at once and lets Postgres order them, so a seed that reaches one replays the same moves but not always the same outcome. The mutant table in `simulate.ts` drops one named constraint, index, or trigger per entry and names the properties it guards, and the simulator must then report one of them. `noMutantYet` in `catalog.ts` lists every other named constraint, index, and trigger under the reason it has no mutant yet. `--mutant all` fails on a name in neither list, and it reads names only from the tables that `catalog.ts` lists as the feature's own, so another feature's migration never fails it. A constraint, index, or trigger that one feature adds to another feature's table carries the adding feature's folder name as its prefix, such as `bridge_token_is_a_hash` on `attempt`. Each catalog calls `auditCatalog` in `tools/verify/catalog.ts`. It skips a name with the prefix of a feature in `catalogOwners`, claims every name with the calling feature's own prefix on any table, and fails a `noMutantYet` entry that is not the feature's own guard, so each guard has one owner and nothing escapes both catalogs. A prefix of a feature missing from `catalogOwners`, such as `jira_`, stays in the catalog of the table's owner. The tasks feature owns `human_action`'s constraints, so its catalog holds the mutants of `one_target` and `target_fits_kind`, which cover the repository and connector targets. `simulate.test.ts` is the fast gate that `npm test` runs. The `<name>-sim` verify scenario runs the fault profiles, the plants, and the mutants. It declares `nightly`, which returns the argument lists of its nightly runs for a day number, one list per run. `npm run verify -- sims` runs every scenario whose name ends in `-sim` with the arguments that follow `sims`, and the `sims` job in CI runs `sims --mutant all`, then the fault profiles that `--mutant all` skips, one step per simulator. `npm run verify -- sims nightly --shard <k>/<n>` runs share k of n of every simulator's nightly runs, fails a simulator that declares none, and the nightly workflow runs each share as one job, so a new simulator needs no workflow edit. Each run counts the tasks that ended done, and both the scenario and the fast gate fail a seed that took no task to done. `--trace <dir>` writes a failing seed's own full trace as soon as that seed fails. A seed that failed and was then fixed goes into `failed-seeds.ts` with the simulator's fingerprint, a hash of its moves and profiles. The fast gate replays every entry and fails one whose fingerprint no longer matches, because a changed simulator no longer replays the old failure. Re-record such an entry. `features/tasks/` is the example.
- **Plug-in points.** A rule that a fork may change is one typed value that `services/engine/main.ts` passes in, and the core calls only that value. A fork replaces the value there with its own rule of the same type, such as one that adds a condition on the ticket, and keeps taking upstream changes. `features/tasks/run-as.ts` is the example. It exports `RunAsRule`, which takes the task and returns the person or team account an attempt runs as, or `null`, the core rule `coreRunAs`, which takes the routine's fixed identity or else the ticket's current Jira assignee read just before the claim, and `nobodyToRunAs`, the waiting reason a task shows when nobody can run it. The worker resolves the rule before each claim and passes the identity into `claim`, which refuses a claim with no identity and parks the task with that reason. The simulator claims through `coreRunAs` too.
- **Workflows.** A workflow is `features/<name>/workflow.ts`, which exports `workflow`, an object literal with a literal `name` and a list of `step({ ... })` calls, each with a literal `name`, written `as const satisfies Workflow`. `step` in `shared/workflow.ts` is the only way to build a step kind. It derives `judge`, which turns the agent's final message into the step's verdict, from the declared `output` schema, the block kinds a done review `requires`, the `blocked` verdict for a review that is unreadable, blocked, or missing a required block, and `done`, which maps a done review to a verdict. A verdict that comes from outside the agent, such as a red check on a pull request, is declared in `failures` like any other, and the code that observes it passes it to `advance` as the observed verdict. tsc rejects a step kind written as an object literal, a `blocked` or `done` verdict that `failures` does not declare, and `needs_input` routed to anything but `ask`, and `guardrails` proves the first three. `workflowsByName` rejects a step kind that `step` did not build, such as a copy made by spreading one. The engine runs a workflow once `services/engine/workflows.ts` lists it, and `services/engine/main.ts` refuses to start while a routine's newest version, or a version with an unfinished task, names a workflow that list lacks. `npm run verify -- engine-start` runs the entry point against Postgres both ways. A workflow's own `verify.ts` checks its declaration against the shape the task model checks and runs each step's `judge` on reviews of every outcome, as `npm run verify -- code-change` does. The simulator runs its own copy of Code change, because a feature never imports another, and `tasks-sim --mutant all` checks that copy against the same shape. CI runs all three. The runner never names a workflow or a step. `npm run step-names` runs `tools/step-names/main.ts` as part of `npm run check`. It parses each `features/*/workflow.ts` as text, and it fails when a file under `features/tasks/` or `services/engine/` names a declared workflow or step in a string, a single-quoted token inside one, a property key, or a property access. It skips tests, which check the runner rather than run it, and the simulator's files in a feature folder: `verify.ts`, `simulate.ts`, `invariants.ts`, `catalog.ts`, and `failed-seeds.ts`. `services/engine/workflows.ts` may name workflows but not steps. A step named like one of the runner's own words, such as `approve` or `done`, trips the check, so give it another name. The engine sends each agent step's `outputSchema` to Codex in strict mode, which fails the turn when an object leaves a property out of `required`, so a field with no value is required and nullable, never optional. `npm run strict-schemas` runs `tools/strict-schemas/main.ts` as part of `npm run check`. It checks every agent step of every workflow in `services/engine/workflows.ts`, and it fails on a root that is not an object, an object without `additionalProperties: false` or with a property that `required` lacks, `oneOf`, `allOf`, `not`, a conditional, `patternProperties`, a `$ref` to a missing schema, and an `anyOf` member whose first property is not the one-value field, such as `kind`, that the other members start with. Codex writes an object's first key before it picks the member, so it cannot reach a member that starts with another key. The engine stores the schema as `json`, not `jsonb`, because `jsonb` sorts keys and would move `body` ahead of `kind`. `features/code-change/` is the example.
- **Budget.** `budget/budget.json` lists the areas the codebase is budgeted by, each with a ceiling and a why (B6). Each role is a list of globs, and a file counts toward the first role whose globs match it, after `exclude`. Each role has three ceilings: non-blank `lines`, non-whitespace `characters`, which joining lines cannot shrink, and `longest-line`, which only goes down. Separate roles keep verification code, the e2e harness, tools, models, migrations, and docs from being deleted to make room for product code. `structure` counts features, services, migrations, tables, named constraints, indexes, and triggers, TLA+ models, runtime and dev dependencies, verify scenario declarations, and CI jobs and steps. `npm run budget` fails on any count over its ceiling, and on a `ci.yml` job without a time ceiling. `states` holds each model's distinct state count under its pull request config, which `npm run verify -- models` checks after TLC runs. `seconds` holds each CI job's wall time, about twice what recent runs took, which `node tools/ci-local/main.ts` enforces by stopping a job that passes it. To raise a ceiling, a unit runs `npm run budget -- --raise <unit> --why "<why>"`, which writes `budget/raises/<unit>.json` with the amount each count is over, and commits that file alone. It adds `--add states/<Model>=<n>` or `--add seconds/<job>=<n>` for a count the static check does not measure. Each unit writes its own raise file, so two units' raises merge without a conflict, and the ceilings are the file's plus every raise. A unit never edits `budget/budget.json`. After each landing, the coordinator runs `npm run budget -- --lower` in a clean worktree, adding `--states <models log>` when local CI ran the models job on the landed commit. It sets every line and structure ceiling, and each state count the log reports, to the landed count, never raises one, folds in and deletes the raise files, and prints their whys for the commit message. It never lowers a time ceiling. `npm run budget -- --since <rev>` fails when a commit in `<rev>..HEAD` that is not a merge raises a ceiling, or changes the roles, whys, or exclusions, and also changes a file outside `budget/`. The `check` job runs it from the pull request's base through `--since-pr-base`, which checks nothing outside a pull request, so pass `--since` locally. Run `--lower` and `--since` where git can read the worktree, as `node tools/budget/main.ts` does on the host, because git inside the verify container cannot read a worktree made on Windows.
- **Engine loops.** The engine is one program, `services/engine/main.ts`, that runs every loop until SIGTERM. A loop is a `Loop` from `shared/loop.ts`, built by a function in its feature folder: a `name`, an interval `everyMs`, and a `pass` that takes the database and the pass's `now` and returns one log line per thing it did. A loop whose pass depends on how long the engine was away from Postgres also gives a `resume`, which runs before its first pass and again after any pass that fails. `runLoop` runs a loop at a fixed rate, logs a failed pass and keeps going, and on SIGTERM lets the current pass finish before the loop stops. To add a loop, add its setting to the zod `settings` object in `services/engine/main.ts`, which reads the environment once, and add the loop to `loopsFor` there. Pass it only the values it needs, not the settings object. Its simulator runs the same `Loop` through `runLoop` on a virtual clock, so each property it checks sees the real pass. `reaper` in `features/tasks/reaper.ts` is the example.
- **Person requests.** A person's action on a task or a routine reaches the engine only as a `person_request` row, which `request` in `shared/requests.ts` writes, so the command line and the dashboard share one path (A3). The caller makes the request's id, a uuid. A repeat with the same id returns the first row, and a repeat whose person, target, kind, or details differ is refused as `id-taken`. The trigger `request_takes_next_place` gives each request the next place in its target's line, the highest place so far plus one, and the unique constraint `one_request_per_position` makes an insert that raced another for the same place fail, so `request` retries it and places follow commit order, never a caller's clock. `request` refuses a transaction, because a failed insert would end it. The `dashboard` role can read requests and insert only their question columns, never a place or an answer. The engine's `requests` loop in `features/requests/apply.ts` claims the oldest open request of a target with `for update skip locked`, skips a target whose older request another engine holds, and runs the kind's handler, writes the answer, and commits in one transaction per request, so a failing handler holds back only its own target. The request's id is the `human_action` id, and the action's time is when the engine applied it. When a handler throws, its transaction rolls back, and a new transaction refuses the request with a fixed sentence, writing only over an open answer, while the engine log keeps the error. A lost connection, a deadlock, or a serialization failure leaves the request open for the next pass instead. `answer_is_final` refuses any change to an answer and any delete of an answered request. Each transaction sets `statement_timeout` and `idle_in_transaction_session_timeout` to `REQUEST_TIMEOUT_MS`, so a hung engine lets go of its target, and a request that runs out of time is refused with a sentence that says so. `answerOf` returns `waiting`, `recorded` with the action's id, or `refused` with a sentence. To add a kind, add it to `requestKinds` with its target and its zod payload, add it to the `request_kind_fits_target` check in a migration, and add its handler line to the `handlers` record in `services/engine/main.ts`, which `satisfies Handlers<RequestKind>`, so a kind with no handler fails `npm run typecheck`, as `guardrails` proves. A handler takes the transaction and the request, returns `recorded` or `refused` with a sentence a teammate understands, and never waits on a person or an outside service. `features/requests/Requests.tla` models the loop, and `npm run verify -- requests-sim --mutant all` proves that each of its guards can fail. `stop` is the example.
- **External actions.** Every call that changes something outside AutoWorker, such as a comment, a pull request, a branch, or a merge, is an `outbox` row committed in the same transaction as the state that owes it. Owe it with `owe(kind, payload)` from `shared/actions.ts` and the `enqueue` the engine passes in from `features/outbox/enqueue.ts`, whose first argument is the `Transacting` brand that only `inTransaction` in `shared/transaction.ts` makes, so an enqueue outside a transaction fails `npm run typecheck`. Owe it after the attempt that owes it has finished, because a task with an unsettled row is not ready and a live attempt must point at a ready task. A connector adds a kind by writing its zod payload and result as an `ActionSpec`, and its performer with `performer(spec, target)`, where the target either catches a duplicate by itself or looks for the row's marker first. It registers the performer in the `performers` object in `services/engine/main.ts`, which `satisfies Performers<ActionKind>`. The performer sends each request once, within the `deadline` and `signal` it is given. `features/outbox/` is the example.
- **Sources.** A source is how a routine finds work. It is a `Source` from `features/routines/source.ts`: a literal `kind` and a `find` that takes the claimed `RoutineRun`, which names the run, the routine, its occurrence, the person the search acts as, and the routine version's `source` JSON, and returns work items, each with a `key`, a `title`, and the ticket's assignee account where the source has one, or `null`. The key names the task across every routine, so it must be unique forever. A source parses its own fields of the `source` JSON with zod, and throws when the search fails, which the scheduler records on the run with a note. The engine registers each source once in `sourcesByKind` in `services/engine/main.ts`, and a routine names its source by `kind`. A source that needs a credential or a client gets it when `main.ts` builds it, not from the run. `scheduleSource` in `features/routines/schedule-source.ts` is the example, with the key `<routine>/<run>`.
- **Verify providers.** A Verify provider makes the environment a Verify step checks behavior in, one per attempt. The contract is `Provider` in `features/environments/provider.ts`: a `name`, a `start` that returns the agent's own workspace with the command to run there, the workspace with the checks from the repository's CI config, or an address the agent can reach, and a `stop`, both idempotent per attempt id. `start` creates nothing once its `signal` aborts at the start deadline: a provider still making an environment then cancels it or stops it itself, because the engine may already have recorded the stop, and nothing stops an environment that lands later. `npm run verify -- environments-sim --mutant provider_honours_deadline` shows the leak a late answer causes. A provider keeps its credentials in the engine and never returns one, so a Job needs no cluster access. Each repository row names its provider in `verify_provider`, which defaults to `tests-only`, and `features/environments/tests-only.ts` is the example. A fork adds its own provider in its own feature folder, `features/<name>/provider.ts`, which exports a plain object of the same shape and imports nothing from `features/environments/`, because features never import each other. It passes that object to `providersByName` in `services/engine/providers.ts`, which the engine and setup share, where tsc checks it against `Provider` by its structure, and it changes nothing under `features/environments/`. `providersByName` always adds `tests-only`, and it refuses a name that is not a slug or that two providers share. The engine refuses to start while a repository, or an environment nobody has stopped, names a provider it was not given. `startEnvironment` records each start before calling `start`, and the `environments` loop calls `stop` for every environment whose attempt has ended and records the stop only once no start can still land. `npm run verify -- environments-sim` checks both in the simulator.
- **Attempt Jobs.** Each attempt runs as a Kubernetes Job from the attempt image, `services/job/Dockerfile`. The image pins its base by digest and the Codex CLI by version, the same pins as the verify image, and `npm run verify -- jobs` fails when they differ. It holds two users. `bridge` runs the entry point, `tini -- node-bridge /app/services/job/main.ts`, where `node-bridge` is a copy of `node` that only `bridge` can run and that may start processes as another user. `codex` owns the workspace at `/workspace` and the Codex home, and runs Codex, so the agent cannot read the bridge's environment. The bridge fetches, commits, and pushes through its own git directory, `/var/lib/autoworker/attempt.git`, with `/workspace` as its work tree. The agent can read that directory but not write it, so it cannot change what a push sends or where, and the GitHub token stays in the bridge's processes. The entry point runs from the image and never from the clone. A repository may name its own public image in `repository.job_image`, which must extend the attempt image, and the column accepts only a reference with a digest. Private registries and images that are not public belong to a fork. `manifests` in `features/jobs/launch.ts` builds a Job and a per-attempt Secret from a `LaunchInput`, whose Codex login is an `AccessOnlyLogin`, and `launch` applies them idempotently, with the Secret owned by the Job. The Secret's keys are `SecretKey` in `features/jobs/workspace.ts`, and the Job parses them with zod. The Job has `backoffLimit: 0`, `restartPolicy: Never`, `podReplacementPolicy: Failed`, the deadline from `JOB_DEADLINE_SECONDS`, no service account token, and a service account with no role binding. It holds no database or Kubernetes credential, and it may reach only its repository, the engine's address, and the Codex API. The sweep in `features/jobs/sweep.ts` deletes every labeled Job and Secret whose attempt is finished or has no row, so a namespace holds the Jobs of one AutoWorker only. `features/jobs/` is the example.
- **Engine endpoints.** An engine endpoint is served from `services/engine/main.ts` on a listener the engine opens before its loops start, and closes on SIGTERM. Its handler lives in the feature folder and is built by one function that takes the database and only the values it needs, as `bridgeListener` in `features/bridge/engine.ts` is. Every message either side sends is a zod schema in the feature's `protocol.ts`, and the endpoint parses every header, query, and body with it before it reads anything else. Every call carries the attempt's id and `Authorization: Bearer <token>`, and the engine keeps only the token's SHA-256 hash, compared in constant time. The first call binds the attempt to the caller's process id, and a call from any other process is refused. The caller sends its protocol number, and a mismatch is refused with a reason that names the caller's image. Each refusal is a JSON body with a kind and a reason, under one fixed status per kind. Every writer takes the attempt row `FOR UPDATE` and refuses an attempt that has ended, and a trigger refuses the same insert, so a missed check still cannot write. The endpoint answers only after its transaction commits. The handler's rules sit behind one `Rules` value so the simulator can swap a broken rule in and show that its property fails. `features/bridge/` is the example.
- **Connectors.** A connector is a feature folder that talks to one outside service. It holds a client, the performers for the action kinds it registers, and a check of its credential in `features/credentials/`. The client parses with zod every field it reads, sends each request once with no retry, and exposes only the calls its performers and reads use. Its performers are one record typed over its kinds, `Performers<Kind>`, so a missing performer fails `npm run check`, and the engine spreads that record into its performer map. A performer counts a duplicate the service refuses as its own success and reads the result back, names the state it expects to replace, and reads every page of a lookup. A connector's simulator runs its real client against a seeded fake of the service. `features/github/` is the example. The core never approves a pull request, so no client exposes a submitted review.
- **Screen checks.** Every dashboard screen passes the 19 objective gates in `tools/verify/screens/gates.ts` and a review against `tools/verify/screens/rubric.md` by reviewers who never see each other. A feature declares its screens by exporting `screens` from its `verify.ts`, each a `Screen` from `tools/verify/screens/screens.ts` with a name, a group from the rubric, a path, the seed it needs, the browser steps to run first, and the height to capture. `npm run verify -- screens <group or all>` captures each screen at 1440 by 900 in the light and dark themes through `tools/verify/browser.ts`, measures it with `tools/verify/screens/measure.ts`, and judges every gate. Capturing a declared screen needs the local engine at its seed and the dashboard, so until those land `screens` fails any declared screen. Every run also captures the frozen busy task page, `fixtures/task-a-live.html`, which must fail at least one clutter gate, or the run is void and fails. `npm run verify -- screen-gates` judges both fixtures and requires the revised task page, `fixtures/task-a-revised.html`, to pass every gate. It matches both against `fixtures/round-4.json` within 2 words and 1 box, captures the revised page twice more and requires the same metrics and under 0.1% of pixels changed, and fails when one screen takes over 6 s at the median. `--video <seconds>` also records the revised page and checks a frame of the video against its screenshot. `guardrails` plants each gate's violation from `tools/verify/screens/plants.ts` in a copy of the revised page and passes only when that gate fails, so a new gate needs a plant, which `npm run typecheck` requires. `npm run verify -- screen-review <group> --fixtures` writes a packet for the reviewers to `.shots/screen-review/<group>/`, and `screen-review <group> --judge` checks the returned reviews against the packet's `review.schema.json`, which `packet.ts` generates from its zod schema. A screen passes with every review scoring it 4 or higher on every scored dimension. A group passes when every screen passes, every reviewer scores consistency 4 or higher, and every reviewer confirms the empty, busy, waiting, and error coverage. `limits.json` holds the limits, which stay fixed, so a page that fails one gets fixed, not the limit. `limits.words` counts the words of one view above the fold, the page with its open tab, and `reviewers` is the number of reviews each group needs. A script that runs in the page is a typed function over the few DOM members it reads, which `run` in `browser.ts` sends to the page as source, because the root tsconfig has no DOM library. Save screenshots, videos, and packets under `.shots/`, which git ignores.
