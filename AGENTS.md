# Rules for autoworker-oss

These rules apply to every change in this repo, whether an agent or a person wrote it. [docs/spec.md](docs/spec.md) specifies the system these rules build. [docs/decisions.md](docs/decisions.md) records the settled design decisions and the options that lost. Do not reopen a settled decision without new evidence. Every rule has an ID. Cite IDs in reviews and commit messages, for example `move parser into its feature folder (A4)`.

## The rule behind the rules

When an agent makes a mistake, or when you are about to leave a review comment, fix the cause at the highest level that works:

1. **Architecture**: make the mistake impossible through types, data structures, or module boundaries.
2. **Static checks**: compiler, type checker, lint, CI. A violation must fail the build.
3. **Guidance**: this file, skills, AI review. Useful, but an agent can skip it.
4. **Human review**: the last resort. A review comment that keeps coming back points to something missing in levels 1 to 3.

Never fix a repeated mistake only by rewording a prompt. Most rules below are enforced by this file alone for now; the [enforcement table](#enforcement) tracks moving each one up to a check.

## A. Codebase design

- **A1. The codebase is the example.** Agents copy the patterns they see. Merge only code you would be happy to see copied everywhere.
- **A2. The shortest path is the correct path.** Agents take the quickest route. If the quick way to do something is wrong, change the codebase until the quick way is right.
- **A3. One paved path.** Each kind of thing (feature, command, config, test) has exactly one approved way to build it, recorded under [Paved paths](#paved-paths). Do not add a second way. If the paved path does not fit, change it in its own PR.
- **A4. A feature lives in one folder.** All code for a feature, including logic, interface, tests, and fixtures, lives in `features/<name>/`. Code moves to a shared module only when a second feature needs it.
- **A5. Boundaries are checked by machine.** Which modules may import which is declared in config and checked in CI, not left to convention.
- **A6. Design for the contributor with the least context.** A newcomer, a non-engineer, or a small model should be able to add a feature by copying an existing one. Accept constraints that feel heavy to humans; agents absorb the friction.
- **A7. Prefer strict tools.** Choose languages, compilers, and settings that turn mistakes into build errors, and enable their strictest modes.

## B. Keeping the codebase clean

- **B1. No code comments.** Names, types, and structure carry meaning. If code needs a comment to be understood, restructure it. If it is a workaround, fix the cause or open an issue. Agents write comments that go stale and treat workaround comments as permission to repeat the workaround. The only exceptions are lines a tool needs in order to run, such as a shebang.
- **B2. No suppression directives.** No `eslint-disable`, `@ts-ignore`, `noqa`, `#[allow]`, or similar. If a check is wrong, change its config in its own PR.
- **B3. No quiet workarounds.** One merged workaround becomes the pattern within days. Fix the cause, or record it as an issue and stop.
- **B4. Stop the bleeding first.** When you find a bad pattern, first add a check that blocks new instances, then remove the existing ones in follow-up PRs.
- **B5. Delete freely.** Remove dead code, unused exports, and stale docs when you find them.

## C. Verification

- **C1. Agents verify their own work.** Every change is run for real: the app, the CLI, the service. Report the exact commands you ran and what you observed. "Should work" is not verification.
- **C2. One verification tool.** Verification lives in a checked-in tool that agents extend. Do not write throwaway scripts each session.
- **C3. Keep the feature map current.** [docs/feature-map.md](docs/feature-map.md) lists every user-facing feature: what it does, how to reach it, and where its code lives. Update it in the same PR as the feature.
- **C4. Correct is not the same as good.** Verification proves a change works. Quality comes from sections A and B.
- **C5. Model concurrent protocols before building them.** Code that coordinates concurrent actors, such as claims and leases, the stage machine, the outbox, or event delivery, gets a TLA+ model before the code is written. The model runs in CI whenever it or the code it covers changes, and the verification skill says how to run it.
- **C6. Put invariants in structure and check behavior by simulation.** Put each invariant where the build or the store enforces it, in a type, a schema constraint, or a TLA+ property, and prove it can fail with a negative control, such as a planted violation or a mutant. Check behavior by running the real code in a seeded simulation that injects faults and checks those invariants after every step. Write a unit test only for a pure function whose logic a simulation cannot reach, and never one that restates the code.

## D. Adding a feature

- **D1. Copy the closest example.** Find the most similar existing feature and follow its shape.
- **D2. Reproduce before fixing.** For a bug, show the failure with the verification tool before changing code.
- **D3. Do not guess.** Read the code the change touches. If you cannot find evidence for a claim, say so.
- **D4. Small, atomic PRs.** One idea per PR, so history stays readable and reverts stay cheap. Split large changes.
- **D5. Finish the whole change.** Tests, the feature map, and paved-path docs are updated in the same PR as the code.

## E. Working with agents

- **E1. Repeated corrections become checks.** If you correct an agent for the same thing twice, apply the ladder above.
- **E2. Skills come from observed failures.** Write or change an agent skill only after watching an agent fail at something specific. Test the change with an eval before relying on it.
- **E3. Autonomy is earned in steps.** Watched local agents come first, then background or cloud agents, then auto-merge. Move up a step only when verification (C1, C2) and the checks in the enforcement table are in place.

## Stack

Each tool below is the only approved tool for its job (A3). To replace one, or to add a second tool for the same job, change this list in its own PR.

- **Language.** TypeScript on Node 24 LTS, with `strict`, `noUncheckedIndexedAccess`, and `exactOptionalPropertyTypes` on.
- **Lint.** ESLint with typescript-eslint `strictTypeChecked`, typed from the root tsconfig, from one config at the repository root, run only through `npm run lint`.
- **Boundaries.** dependency-cruiser, from `.dependency-cruiser.json`, run only through `npm run boundaries`.
- **Database.** Postgres. The schema lives in plain SQL migrations that `dbmate` runs. Invariants are schema constraints.
- **Queries.** Kysely, with types that `kysely-codegen` generates from the database. No ORM.
- **Outside data.** zod parses every payload, file, and environment variable where it enters.
- **Secrets.** The app encrypts secrets with AES-256-GCM from `node:crypto` before they reach Postgres. The key comes from a Kubernetes Secret and never reaches the database.
- **Tests.** Vitest against a real Postgres that Testcontainers starts. No database mocks.
- **Formal models.** TLA+, checked with TLC from `tla2tools.jar` v1.7.4 on Java 21, both pinned in the verify image. A model lives in the feature folder of the code it covers (A4).
- **Dashboard.** Next.js App Router. Server components read Postgres, and server actions write to it.
- **Connectors.** Octokit for GitHub. `fetch` and zod for Jira and Webex.
- **Agent runtime.** The Codex app server (`codex app-server`), pinned to one exact Codex CLI version and run inside each attempt's Job. Use only the protocol's stable methods.
- **Deployment.** Kubernetes.
- **Kubernetes API.** `@kubernetes/client-node` 1.4.0, the release whose types fit `@types/node` 24, with `@types/ws` for the `ws` types it leaves out. Local clusters come from kind v0.33.0, pinned in the verify image for amd64 hosts.

## Paved paths

The first feature, command, or module of each kind defines its paved path. Record it here in the same PR.

- **Layout.** Feature code lives in `features/<name>/`. Entry points live in `services/engine/`, `services/dashboard/`, and `services/job/`, and hold no logic. Each folder directly under `features/` or `services/` is named with lowercase letters, digits, and dashes, and starts with a letter. Code moves to `shared/` only when a second feature needs it. Migrations live in `db/migrations/`, and tools live in `tools/`.
- **TypeScript.** Node 24 runs `.ts` files directly, so there is no build step. Import with the `.ts` extension, use `import type` for types, and write only syntax Node can erase, so no `enum` and no `namespace`. `npm run check` runs `npm run shape`, `npm run sql-comments`, `npm run model-names`, `npm run typecheck`, `npm run lint`, `npm run boundaries`, then `npm run db-types`. `npm run lint` lints against the root ESLint config and the root tsconfig, so a nested config of either kind changes nothing.
- **Verification.** `npm run verify -- <scenario>` runs one scenario, prints `PASS` or `FAIL` per check, and exits non-zero on any failure. A feature's scenarios live in `features/<name>/verify.ts`, which exports `scenarios`. Run everything inside the verify container, which CI uses too. Install with `docker compose run --rm verify npm ci`, again after any change to the lockfile, then run `docker compose run --rm verify npm run verify -- <scenario>`. A live lane, one that reaches the cluster, Jira, GitHub, or Codex, runs in the `live` service instead. `live` runs the verify image with the same mounts. It loads `~/.autoworker/sandbox.env`, which sets `JIRA_SITE`, `JIRA_EMAIL`, `JIRA_API_TOKEN`, and `GITHUB_TOKEN` one unquoted `KEY=value` per line, into its environment when that file exists. It mounts `~/.autoworker/codex/` read-only at `/codex`, where an access-only Codex login sits as `auth.json`. `npm run verify -- accounts` checks the four keys, the Jira and GitHub tokens, and that no mounted login holds a refresh token, and it prints no value. Never run `docker compose config`, print a `live` container's environment, or copy a compose error about the sandbox file into a transcript, because each can show the sandbox values. A lane that uses the cluster runs `npm run verify -- kind up` first in its own container, as in `docker compose run --rm live sh -c 'npm run verify -- kind up && npm run verify -- <scenario>'`, because the container's place on the `kind` network and the kubeconfig that `kind up` writes to `~/.kube/config` last only as long as the container. `kind up` creates the `autoworker` cluster that `tools/verify/kind.yaml` pins, or reuses it when its node runs the pinned image. Every worktree on the machine shares that cluster, so `kind up` never deletes a running one and recreates only a stopped one. `kind down` deletes it for everyone, so run it only when no other lane uses it.
- **Guardrails.** Every check that enforces a rule gets a case in `tools/verify/guardrails.ts`. The case plants a violation in a copy of the repository and passes only when the check rejects it. An exception the check allows gets an allowance case that plants the allowed line and passes only when the check accepts it, beside cases that prove the exception allows nothing more. Each check is an npm script, and a case runs that same script, so it proves the check CI runs. For each script that `npm run check` chains, one case runs `npm run check` itself, so a script dropped from the chain fails too. The case for `npm run verify -- models` runs in a copy without `features/`, so its plant is the only model and the guardrails never rerun the real models.
- **Checks.** A check that no tool in [Stack](#stack) can express is our own script at `tools/<name>/main.ts`, run as `npm run <name>` and chained into `npm run check`. It prints one line per violation, starting with the path it rejects, and exits 1 when there is any. It adds no tool, so Stack does not list it. A check that only reads files runs before `npm run typecheck`. A check that starts a container, such as `npm run db-types`, runs last, so the fast checks fail first. A check that reads product code parses it as text and never imports it, because `tools/` imports no product code. `npm run model-names`, for example, parses `invariants.ts` with the TypeScript compiler API. `tools/shape/` is the example.
- **Boundaries.** `.dependency-cruiser.json` declares them, and `npm run boundaries` enforces them as part of `npm run check`. The rules read static imports and re-exports. Imports only point down: `services/` may import `features/` and `shared/`, `features/` may import `shared/`, and `shared/` imports neither. Features never import each other, and no service imports another. `services/` and `shared/` never import `tools/`, because they deploy and must not pull in verification tooling. The rule is `product-code-imports-no-tools`. Features may import `tools/verify/`, which holds the verify scenarios' shared helpers and the Postgres harness, `tools/verify/postgres.ts`. Neither `tools/` nor a file outside a feature folder, a service folder, `shared/`, or `tools/` imports product code by a static import, so neither can carry one module to another. The verify tool loads each `features/<name>/verify.ts` by a computed import, which the rules do not see. `npm run shape` runs `tools/shape/main.ts` as part of `npm run check`. It rejects every symbolic link, so the rules and lint see each file at its real path. It rejects a `node_modules` folder below the root, because the rules and lint skip the code inside one. Agent tooling under `.claude/` may install its own packages. It also rejects any folder directly under `features/` or `services/` whose name does not match `^[a-z][a-z0-9-]*$`, because the rules put that name into a pattern. It reads the files on disk, ignored ones included, and skips the root `.git` and `node_modules`. So a link that npm makes in the root `node_modules` for a `file:` dependency or a workspace still gets past it. Code in `services/job/` never imports a Postgres client, `kysely`, `shared/db/`, or a `@kubernetes` package, even through a helper. No import rule can see `fetch`, a raw socket, or a module loaded by a computed name, so the Job's pod spec stays its runtime boundary. No import is circular or orphaned.
- **Migrations.** A migration is `db/migrations/<YYYYMMDDHHMMSS>_<name>.sql`, plain SQL that dbmate runs. Write its `-- migrate:down` part to undo exactly what its `-- migrate:up` part does. `npm run verify -- migrations` proves it in CI. It applies the migrations one at a time, then rolls them back one at a time, and after each rollback it requires the schema to match what it was before that migration applied. Last, it applies them all again. A migration holds no comment except those two marker lines, each alone or followed by dbmate's `transaction:false` option, and no `COMMENT ON`, which kysely-codegen would copy into the generated types. `npm run sql-comments` rejects both, inside a dollar-quoted function body too. Name every check, unique constraint, foreign key, index, and trigger for the rule it enforces. Also name a not-null that a guard relies on, such as `attempt_runs_as_a_person`, and the not-nulls under the MATCH SIMPLE foreign key `live_attempt_matches_ready_task`, which skips a row that holds a null in any of its columns. Other not-nulls and primary keys keep the names Postgres gives them, and the simulator's catalog check skips those default names. No column defaults to `now()`. A statement that reads or writes a time takes it as a `Date` parameter, so the simulator can run it on a virtual clock. `shared/db/types.ts` is generated from the migrated schema and never edited by hand. Run `npm run db:types` in the same PR as the migration to regenerate it. Resolve a merge conflict in `shared/db/types.ts` the same way, by running `npm run db:types`, never by a hand merge. `npm run db-types` runs last in `npm run check` and fails when the file differs from a fresh generation. `db/migrations/20260923220000_tasks.sql` is the example.
- **Queries.** Product code reaches Postgres only through Kysely. Open a client with `connect(url, connections)` from `shared/db/client.ts`, and take the URL from the engine's settings, which parse `DATABASE_URL` with zod. Build each statement with Kysely's query builder. Use its `sql` template only for a statement the builder cannot express. When Postgres may refuse a statement, catch the error and pass it to `refusal()` from `shared/db/client.ts`. It returns the kind and the name of the constraint or trigger that refused the statement, or the table and column of a refused not-null, and `undefined` for any other error. Map each refusal the statement expects to a value of your own, and rethrow any other error. A test or a verify scenario starts Postgres with `withPostgres` from `tools/verify/postgres.ts`. That harness lives in `tools/`, not in `shared/`, because `shared/` deploys. `features/tasks/claim.ts` is the example.
- **Secrets.** A person's credential reaches Postgres only through `replace` in `features/credentials/store.ts`. It reads the secret with its connector kind's reader in `features/credentials/kinds.ts`, seals it with `features/credentials/seal.ts`, and calls `replace_credential`, a `security definer` SQL function that records the replacement as a `human_action` and writes the credential in one statement. `seal.ts` uses AES-256-GCM from `node:crypto` with a fresh 12-byte nonce per seal and the credential's connector and owner as additional data, so a sealed value moved into another row fails to open. The key version is stored beside the ciphertext. A service reads its key once at startup with `sealingKey(process.env)`. It parses `CREDENTIAL_KEY`, base64 of exactly 32 bytes such as the output of `openssl rand -base64 32`, and `CREDENTIAL_KEY_VERSION`, a positive whole number. `SealingKey` carries a brand that only `sealingKey` adds, so an object literal cannot pass for a key. The key comes from a Kubernetes Secret and never reaches Postgres, a log, or an error message. The engine reads a credential with `open`, which names each failure: no credential, another key version, or a failed GCM check. On success it also returns the `action_id` of the replacement it read, so a later write can require that nobody replaced the credential since. The `dashboard` role can select every `credential` column except `ciphertext` and can execute `replace_credential`. It cannot insert or update a credential or a `human_action` itself, so every write it makes is recorded. The dashboard service connects as a login role that is a member of `dashboard`. Roles belong to the whole Postgres cluster, so one cluster holds one AutoWorker database, and the user that runs migrations needs `CREATEROLE`. A replacement carries the action id its caller made, so a replayed id writes nothing, and a replay of a write that still stands returns that write. A Codex login that holds a refresh token is stored only when its caller says it was made for AutoWorker, because the engine's refresh signs out every other copy of that login. Postgres cannot use an enum value in the transaction that adds it. So a new connector kind adds its value to `connector_kind` in a migration of its own, as `db/migrations/20260923232000_credential_kinds.sql` does for `human_action_kind`, and then its row to `connector` in a later migration and its reader to `kinds.ts`, which `npm run typecheck` then requires. `npm run verify -- credentials` proves the store. `npm run verify -- credentials --mutant all` proves that each named guard and each missing privilege can fail. `npm test` runs both through `features/credentials/store.test.ts`, so CI enforces them. `features/credentials/` is the example.
- **Admin commands.** An admin command is a file in `services/engine/` that an admin runs with `node`, such as `node services/engine/setup.ts <file>`. It parses all of its input with zod before it writes anything, and it hands each part to the feature that owns it, which exports the part's schema and the function that applies it. It never prints a secret. Its input names each secret by an environment variable or a file path and never holds one, a zod message names the field and never the value, and a secret reaches Postgres only through `replace` in `features/credentials/store.ts`. It is idempotent: it matches each record by a natural key, writes only what differs, applies each section in one transaction, and prints one count per section. Its verify scenario runs it as a child process against a fresh database with made-up secrets, and checks that no output holds one. `services/engine/setup.ts` is the example.
- **Credential checks.** Each connector kind brings its own check. `checksFor` in `features/credentials/checks.ts` returns a record typed over `ConnectorKind`, so a kind without a check fails `npm run typecheck`. A check takes the opened secret and returns `valid`, `invalid`, or `unknown` with a cause, the expiry it learned, and `rotated` when it rewrote the secret. Its `rotates` says whether it may use a refresh token. The engine's `checks` loop in `features/credentials/check-loop.ts` claims a check with one insert into `credential_check`. The partial unique index `one_live_check_per_credential` lets one check run per credential, and `one_refresh_per_login` lets only one check ever try to refresh a given login, because a refresh token works once. When such a check loses its lease, the next check records the login `invalid` instead of refreshing it again. A rotated login goes back through `writeBack` in `features/credentials/store.ts`, which writes only over the login the check opened, with the same replacement and expiry, and only when the new expiry is later. The loop checks a credential after each replacement, and a Codex login once more inside its 5-minute refresh window, and never more often, because one Codex check sends about 13,500 input tokens. `loginForJob` checks a login first when its last check is older than 6 hours, and gives a Job only an `AccessOnlyLogin`. Only `accessOnly` in `features/credentials/kinds.ts` makes one, by blanking the refresh token, so only the engine ever refreshes. The Codex check runs `codex exec` on `gpt-6-luna` in a private temporary Codex home that it deletes on every path. `features/credentials/Checks.tla` models the protocol. `npm run verify -- credentials-sim` runs the real loop with several checkers against a fake issuer that refuses a reused refresh token, and `--mutant all` proves each guard. To add a kind, add its check file, its entry in `checksFor`, and its fake in `features/credentials/simulate.ts`. `features/credentials/codex-check.ts` is the example.
- **Package types.** When a package's own type declarations name a type that no installed package declares, `npm run typecheck` fails. Declare the missing names in `shared/types/<package>.d.ts`, named for the package whose declarations name them, one file per package, and never turn on `skipLibCheck`. For example, vitest depends on tinybench, whose declarations name `DOMHighResTimeStamp`, so `shared/types/tinybench.d.ts` declares it. A package that ships no types and has no approved `@types` package, such as `pg`, gets the same kind of file, which declares only the part of its API the code calls. Each file must be needed, so deleting it brings back a `tsc` error. Delete the file once the package declares what was missing.
- **Formal models.** A model is `features/<name>/<Model>.tla` with `<Model>.cfg`, written before the code it covers. Give each guard in the design a boolean constant that the real config sets to `TRUE`. The feature's `verify.ts` declares the model through `defineModel` in `tools/verify/models.ts`. The declaration names the module, the real config as `pr` and the nightly config as `nightly`, each with a floor for each bound, the guards, each property with its section, the liveness properties, and each mutant with its guard, the property it must break, and an optional trace shape. `defineModel` returns the `<name>-model` scenario, which runs TLC on the real config, then once per mutant with that mutant's guard set to `FALSE` and only its property checked. The scenario passes only when the real config holds and every mutant fails. It first parses the config strictly: `TypeOK` and each invariant sit under `INVARIANTS` and each action or liveness property under `PROPERTIES`, each constant is assigned once, no line holds a comment, every guard is `TRUE`, every property and every guard keeps at least one mutant, and each bound is at or above its floor. So demoting an invariant, shrinking the model, hiding a value behind a comment, or dropping the last mutant of a property or guard fails too. A check of planted configs proves the parser still rejects each of these. Larger bounds go in `<Model>.nightly.cfg`. Every run of the scenario reviews it, and the scenario model-checks it in place of `<Model>.cfg` when it is given `nightly`, so a nightly config that fails its review fails the PR. `npm run verify -- models` runs every scenario whose name ends in `-model` and passes on the arguments that follow `models`. The `models` job in CI runs it on every PR, and the nightly workflow runs `npm run verify -- models nightly`, so a new model needs no workflow edit. `features/tasks/` is the example of a model and its configs. Its `verify.ts` keeps its own copy of the checker until M0b moves the Tasks model onto `defineModel`, so a new model declares itself through `defineModel` instead of copying that file.
- **End-to-end test.** The sandbox, a small TypeScript library with its own lockfile, lives in `features/e2e/sandbox/`. Each run branch, `e2e/run-<id>`, holds that folder alone in a commit with no parent, so main never changes. Its workflow defines one job, `sandbox`, which is the context ruleset 23901469 requires on `e2e/run-*`. The test runs in the `live` service, which loads the sandbox tokens and the read-only Codex login: `docker compose run --rm live npm run verify -- e2e --driver <name>`. A driver plays AutoWorker's part and lives in `features/e2e/driver.ts`. Each frontier step lives in `features/e2e/frontier.ts` and observes the system that owns it, never the driver. Every Jira and GitHub payload passes through `parsePayload` in `features/e2e/payload.ts`, and each schema gets a plant in `e2e-payload`. A new catalog entry is one item in `features/e2e/catalog.ts`, with an acceptance test the agent never sees.
- **Simulation.** A feature whose code coordinates concurrent actors runs that code in a seeded simulation, which checks the model's properties after every step (C6). `features/<name>/invariants.ts` exports `properties`, one object literal keyed by the model's property names, with any check the model does not state beside them. Each entry holds a predicate, a Kysely `sql` template that returns the rows that break the property, and a plant, SQL that breaks the property in a scratch database. In `features/tasks/`, `LiveAttemptWorksTheTaskStep`, `TaskHasItsRepository`, `ApproveNamesTheWaitingReview`, `SendBackCarriesItsNote`, `ActionHasOneTarget`, and `ActionTargetFitsItsKind` are checks that the model does not state. `provePlants` runs each plant in its own scratch database and passes only when the plant's property is reported, so every predicate is shown able to fail. `npm run model-names` fails when a model config lists a name that is not a key of `properties`, `TypeOK` included. It skips a feature whose folder, subfolders included, holds no `.ts`, `.tsx`, `.mts`, or `.cts` file other than its top-level `verify.ts`, because that model landed before its code (C5). It checks the feature once any other such file arrives. `simulate.ts` drives seeded workers on a virtual clock, injects faults, and runs every predicate after each step. `check_step`, the SQL function that runs them, finds the rows a step wrote by their xmin, and xmin identifies those rows only while no other transaction is open. So `check_step` waits up to a second for an older client transaction to end, then raises an error if one is still open. It ignores autovacuum, which can briefly hold a transaction id. Every statement takes the time as a parameter, so a seed replays exactly, except after a `race` move, which runs an attempt's finish, a person action, and two claims on one task at once and lets Postgres order them, so a seed that reaches one replays the same moves but not always the same outcome. The mutant table in `simulate.ts` drops one named constraint, index, or trigger per entry and names the properties it guards, and the simulator must then report one of them. `noMutantYet` in `catalog.ts` lists every other named constraint, index, and trigger under the reason it has no mutant yet. `--mutant all` fails on a name in neither list, and it reads names only from the tables that `catalog.ts` lists as the feature's own, so another feature's migration never fails it. The tasks feature owns `human_action`'s constraints, so its catalog holds the mutants of `one_target` and `target_fits_kind`, which cover the repository and connector targets. `simulate.test.ts` is the fast gate that `npm test` runs. The `<name>-sim` verify scenario runs the fault profiles, the plants, and the mutants. Each run counts the tasks that ended done, and both the scenario and the fast gate fail a seed that took no task to done. `--trace <dir>` writes a failing seed's own full trace as soon as that seed fails. A seed that failed and was then fixed goes into `failed-seeds.ts` with the simulator's fingerprint, a hash of its moves and profiles. The fast gate replays every entry and fails one whose fingerprint no longer matches, because a changed simulator no longer replays the old failure. Re-record such an entry. `features/tasks/` is the example.
- **Plug-in points.** A rule that a fork may change lives in one module, which exports the rule's type and the default rule, and the core calls only that export. A fork replaces the module with its own rule of the same type, such as one that adds a condition on the ticket, and keeps taking upstream changes. `features/tasks/run-as.ts` is the example. It exports `RunAsRule`, `runAs`, and `nobodyToRunAs`, the waiting reason a task shows when nobody can run it, so a fork changes the rule and its instruction together. It is the one module a fork replaces to change who a run acts as. The claim, the step that makes a task wait for a person, and the simulator's check of `TaskChangesOnlyWithItsAttempt` all call `runAs`, so the simulator checks a fork's rule too. A rule may hold a constant only as `sql.lit(...)`, because the simulator compiles the rule into a function body, which takes no bind parameters. `watch()` refuses a rule that passes a constant as a bind parameter.
- **Workflows.** A workflow is `features/<name>/workflow.ts`, which exports `workflow`, an object literal with a literal `name` and a list of `step({ ... })` calls, each with a literal `name`, written `as const satisfies Workflow`. `step` in `shared/workflow.ts` is the only way to build a step kind. It derives `judge`, which turns the agent's final message into the step's verdict, from the declared `output` schema, the block kinds a done review `requires`, the `blocked` verdict for a review that is unreadable, blocked, or missing a required block, and `done`, which maps a done review to a verdict. A verdict that comes from outside the agent, such as a red check on a pull request, is declared in `failures` like any other, and the code that observes it passes it to `advance` as the observed verdict. tsc rejects a step kind written as an object literal, a `blocked` or `done` verdict that `failures` does not declare, and `needs_input` routed to anything but `ask`, and `guardrails` proves the first three. `workflowsByName` rejects a step kind that `step` did not build, such as a copy made by spreading one. The engine runs a workflow once `services/engine/workflows.ts` lists it, and `services/engine/main.ts` refuses to start while a routine's newest version, or a version with an unfinished task, names a workflow that list lacks. `npm run verify -- engine-start` runs the entry point against Postgres both ways. A workflow's own `verify.ts` checks its declaration against the shape the task model checks and runs each step's `judge` on reviews of every outcome, as `npm run verify -- code-change` does. The simulator runs its own copy of Code change, because a feature never imports another, and `tasks-sim --mutant all` checks that copy against the same shape. CI runs all three. The runner never names a workflow or a step. `npm run step-names` runs `tools/step-names/main.ts` as part of `npm run check`. It parses each `features/*/workflow.ts` as text, and it fails when a file under `features/tasks/` or `services/engine/` names a declared workflow or step in a string, a single-quoted token inside one, a property key, or a property access. It skips tests, which check the runner rather than run it, and the simulator's files in a feature folder: `verify.ts`, `simulate.ts`, `invariants.ts`, `catalog.ts`, and `failed-seeds.ts`. `services/engine/workflows.ts` may name workflows but not steps. A step named like one of the runner's own words, such as `approve` or `done`, trips the check, so give it another name. `features/code-change/` is the example.
- **Engine loops.** The engine is one program, `services/engine/main.ts`, that runs every loop until SIGTERM. A loop is a `Loop` from `shared/loop.ts`, built by a function in its feature folder: a `name`, an interval `everyMs`, and a `pass` that takes the database and the pass's `now` and returns one log line per thing it did. A loop whose pass depends on how long the engine was away from Postgres also gives a `resume`, which runs before its first pass and again after any pass that fails. `runLoop` runs a loop at a fixed rate, logs a failed pass and keeps going, and on SIGTERM lets the current pass finish before the loop stops. To add a loop, add its setting to the zod `settings` object in `services/engine/main.ts`, which reads the environment once, and add the loop to `loopsFor` there. Pass it only the values it needs, not the settings object. Its simulator runs the same `Loop` through `runLoop` on a virtual clock, so each property it checks sees the real pass. `reaper` in `features/tasks/reaper.ts` is the example.
- **External actions.** Every call that changes something outside AutoWorker, such as a comment, a pull request, a branch, or a merge, is an `outbox` row committed in the same transaction as the state that owes it. Owe it with `owe(kind, payload)` from `shared/actions.ts` and the `enqueue` the engine passes in from `features/outbox/enqueue.ts`, whose first argument is the `Transacting` brand that only `inTransaction` in `shared/transaction.ts` makes, so an enqueue outside a transaction fails `npm run typecheck`. Owe it after the attempt that owes it has finished, because a task with an unsettled row is not ready and a live attempt must point at a ready task. A connector adds a kind by writing its zod payload and result as an `ActionSpec`, and its performer with `performer(spec, target)`, where the target either catches a duplicate by itself or looks for the row's marker first. It registers the performer in the `performers` object in `services/engine/main.ts`, which `satisfies Performers<ActionKind>`. The performer sends each request once, within the `deadline` and `signal` it is given. `features/outbox/` is the example.
- **Sources.** A source is how a routine finds work. It is a `Source` from `features/routines/source.ts`: a literal `kind` and a `find` that takes the claimed `RoutineRun`, which names the run, the routine, its occurrence, the person the search acts as, and the routine version's `source` JSON, and returns work items, each with a `key`, a `title`, and the ticket's assignee account where the source has one, or `null`. The key names the task across every routine, so it must be unique forever. A source parses its own fields of the `source` JSON with zod, and throws when the search fails, which the scheduler records on the run with a note. The engine registers each source once in `sourcesByKind` in `services/engine/main.ts`, and a routine names its source by `kind`. A source that needs a credential or a client gets it when `main.ts` builds it, not from the run. `scheduleSource` in `features/routines/schedule-source.ts` is the example, with the key `<routine>/<run>`.
