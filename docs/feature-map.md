| End-to-end test | Makes a run branch, `e2e/run-<id>`, from the sandbox folder alone, files an SBX ticket on it, lets a driver take it, and checks each step against the system that owns it: ticket filed, task recorded, plan posted, draft pull request, evidence posted, merged, and clean. The plan and evidence steps read AutoWorker's own comments. Clean waits until the clean check finds nothing left for the ticket: an owed outbox action, a gap or repeat in an attempt's stored events, a fragment left after its item completed, a stored item that does not replay through `shared/items.ts`, an item or turn still in progress in an attempt that passed, a Job or Secret labeled for one of the task's attempts, an unstopped Verify environment, or a branch the record names (an attempt's branch or the pull request's branch) still on GitHub. At clean it checks AutoWorker's record: one done task, attempts in step order with their verdicts, each run as the expected person and on gpt-6-luna, Verify's environment started and stopped once, Verify's evidence failing first and passing second, and replay matching the stored items one for one. It checks the ticket ended in the routine's end status, plants a Secret for a finished attempt and passes only when the clean check names it, and counts the pull requests and repeated comments. Then it posts a report on the ticket, with the timeline, each attempt's duration and agent input tokens, AutoWorker's overhead (time to clean less the agent's turn time), and links to the ticket, the pull request, the merge commit, and both CI runs, and reads the report back. The `autoworker` driver, the default, runs the real engine with Jobs on kind. The `throwaway` driver runs the real agent on gpt-6-luna. The `identity` driver implements the ticket as a function that returns its input, so the acceptance test must fail. | Long-running hold | Holds AutoWorker, the engine and the dashboard, against one repository's base branch until someone stops it. Its one routine searches Jira with `--jql` every `--every` minutes and takes each ticket it finds to a pull request merged into the base, so several tasks run at once. It opens the world as `e2e` does, seeds the base with the sandbox only in the local world, and writes the setup that `e2e` writes for a run: the owner with their GitHub, Codex, and Jira logins, the repository on `--base`, and the routine, which runs as the owner so an unassigned ticket still runs. The repository gets the commands that `--fast-test` and `--setup` name. Without them, Verify runs the repository's CI checks and the reproduction script runs with no setup step. The dashboard listens on the container's compose-network address and never on the `kind` network, so no attempt's pod reaches it. The engine runs Jobs on kind in the hold's namespace and starts again whenever it exits. The hold is named `hold-<world>-<repository name>-<hash>`, where the hash is the first 6 hex digits of the SHA-256 of its world, agent, repository, and base, and it keeps its state under that name between runs. The Docker volume of that name holds the database, which a Postgres container named `<name>-postgres` serves with durable settings while the hold runs. The namespace of that name holds the Jobs and the Secret `credential-key`, whose key seals the logins, so the key never reaches the database. Each start migrates the database forward with `dbmate up` and writes the setup again. Setup changes nothing that already matches, so a restart adds no second person, repository, or routine, and a changed `--jql` or `--every` becomes a new version of the same routine. The hold prints whether it made the volume, the namespace, and the key or kept them from an earlier hold. A new volume always gets a new namespace, so no Job of an earlier database outlives it. When the database is kept but the key is gone, such as after kind makes its cluster again, the hold makes a new key and setup seals the logins again. A second hold with the same name refuses to start while `<name>-postgres` runs. In the local world, the fake GitHub and Jira start empty on every run, so a kept task's ticket and pull request are gone after a restart. The hold prints the world's Jira and GitHub addresses, the routine, the dashboard's address on the host, `JOB_NAMESPACE`, and `DATABASE_URL`, and checks that the dashboard lists the routine. On SIGTERM or a `stop` line on standard input, it prints a `stop:` line for each step as it goes. It stops the dashboard and kills it after 10 s, because `next start` waits for every open request and a live stream never ends. It then gives the engine 150 s to finish its pass, deletes the attempt Jobs with their Pods and Secrets, stops Postgres, keeps the volume and the namespace, and exits 0 when the engine stopped by itself. It seeds nothing on GitHub and never changes the base branch. A kept database remembers each ticket's task, so a restart does not redo a ticket. `--fresh` makes a new hold find every matching ticket again, and a search that ends in `AND status != Done` keeps it from redoing finished tickets. | `docker compose run --rm -T -e GITHUB_TOKEN -p 127.0.0.1:4860:4860 live node tools/verify/main.ts e2e-hold --repository <owner/name> --jql "<search>"`, then open `http://127.0.0.1:4860`. To restart the hold with its kept state, run the same command again from any worktree. To start over, add `--fresh`, which deletes the volume and the namespace first. `--base` defaults to `main`, `--every` to 1 minute, and `--port` to 4860. The sandbox world takes only `--agent real`. `--world local` runs offline in the `verify` service against the fake GitHub and Jira, with the sandbox's commands and the Codex stand-in unless `--agent real`. Run `node` as the container's command, not `npm run`, because `npm run` does not pass SIGTERM on, so `docker stop -t 200 <container>` would skip the teardown. A `stop` line works either way. `npm run verify -- local-engine-read --database <url> --namespace <name>` reads a held world from a second shell. | `features/e2e/hold.ts`, `features/e2e/open-world.ts`, `features/e2e/autoworker.ts`, `tools/verify/dashboard.ts`, `tools/verify/postgres.ts` |
