# Feature map

Every user-facing feature, how to reach it, and where its code lives. Update this file in the same PR as the feature (rule C3 in [AGENTS.md](../AGENTS.md)).

| Feature | What it does | How to reach it | Code |
| --- | --- | --- | --- |
| End-to-end test | Makes a run branch, `e2e/run-<id>`, from the sandbox folder alone, files an SBX ticket on it, lets a driver play AutoWorker, and checks each step against Jira, GitHub, and the `task` table: ticket filed, task recorded, plan posted, draft pull request, evidence posted, and merged. Then it posts a report on the ticket. The `throwaway` driver runs the real agent on gpt-6-luna. The `identity` driver implements the ticket as a function that returns its input, so the acceptance test must fail. The `none` driver is the negative control. | `docker compose run --rm live npm run verify -- e2e --driver throwaway`. Add `--driver none --timeout 120` for the negative control, `--branch <run branch>` to reuse a run branch, and `--entry <name>` to pick a catalog entry. `npm run verify -- e2e-branch` prints a new run branch. `npm run verify -- e2e-payload` proves that each payload schema rejects a missing field by name. | `features/e2e/` |
| Code change workflow | Declares Specify, Implement, Verify, and Land, the steps a ticket goes through in one repository. Verify's review says whether the behavior is fixed, still wrong, or could not be checked. Land declares the verdicts the engine will observe on the pull request: a red check, requested changes, and a required approval. | A routine saved with the workflow `code-change`. No screen yet. `npm run verify -- code-change` checks the declaration against the task model and runs each step's judge. | `features/code-change/`, `shared/workflow.ts`, `shared/review.ts` |
| Task steps, gates, and person actions | Decides a task's next step from its workflow when an attempt ends or a person acts, stops at the routine version's last step, holds a task at each gate until a person approves the review, and waits for answers when a step needs input, at most 3 times in a row. A task parks with an instruction when a cap is reached. Stop, Retry, Approve, Send back with a note, and each answer are recorded as the person's actions, and a decision on a review the task no longer waits on is refused. | No screen or engine loop yet. `act` and `advance` in `features/tasks/advance.ts`. `npm run verify -- tasks-sim` runs every behavior against Postgres with a copy of Code change. | `features/tasks/`, `db/migrations/20260924000000_workflow_kinds.sql`, `db/migrations/20260924000100_workflows.sql` |
| Engine start check | Refuses to start while a routine uses a workflow the engine was not given, and names each such routine and the workflows it can use. | `node services/engine/main.ts` with `DATABASE_URL` set. | `services/engine/`, `features/tasks/start.ts` |
| Reaper | Releases every attempt whose lease has expired within one interval, in one statement that checks the lease, and logs one line per release with the task key and how long the lease had been expired. On start, and after a pass fails or Postgres answers later than one interval, it first gives each live attempt a lease of at least one period from then. A pass that took longer than one interval rolls back. On SIGTERM it finishes its pass and the engine exits 0. | `node services/engine/main.ts` with `DATABASE_URL`, and optionally `LEASE_MS` (60000), `REAPER_EVERY_MS` (30000), `DATABASE_POOL_SIZE` (10), and `DATABASE_CONNECT_TIMEOUT_MS` (10000). `npm run verify -- engine-start` runs the engine process. `npm run verify -- tasks-sim --profile crashes`, `db-pause`, or `two-engines` runs the same loop in the simulator, and `npm run verify -- reaper-perf` times it. | `features/tasks/reaper.ts`, `shared/loop.ts`, `services/engine/main.ts` |
| Routine schedule | Runs each routine once per slot of its interval, `routine_version.every`, with Postgres's clock. One engine claims each slot with a lease, and after downtime it claims only the newest due slot, counts the slots it covers, and closes expired runs of older slots as lost. It runs the routine's source by kind as the routine's run-as person, or else its creator, and records one task per new key and the run's finish in one transaction that checks its claim, so a run whose lease lapsed records nothing. A key another routine owns stays with it, and the overlap is recorded. A search that fails is recorded on its run with a note. A paused routine starts no run, and a run in flight when it paused records nothing. Run now waits as one press per routine and is refused on a paused routine with "Resume to run." The `schedule` source makes one task per run keyed `<routine>/<run>`. | `node services/engine/main.ts`, with optional `SCHEDULER_EVERY_MS` (10000) and `ROUTINE_LEASE_MS` (300000). Setup's `everyMinutes` sets a routine's interval. No screen yet for pause, resume, and Run now, which are `pause`, `resume`, and `runNow` in `features/routines/actions.ts`. `npm run verify -- routines-sim` checks every property of `Schedule.tla` after each step, `routines-engine` runs the engine for 3 minutes, and `routines-perf` times a pass over 100 routines. | `features/routines/`, `db/migrations/20260924120200_routine_runs.sql`, `services/engine/main.ts` |
| Setup from a file | Sets up people, team accounts, each one's GitHub token, Codex login, and optional Jira login, repositories, and routines from one JSON file. The file names each login by an environment variable or a file path and never holds it, and setup refuses a login written inline by its field. It seals each login through the credential store, which records the replacement as the admin's action, and it stores a Codex login that holds a refresh token only when the file marks it `madeForAutoWorker`. A routine's `everyMinutes` sets its interval, 15 by default. It matches a person or team account by email, a repository by name and branch, and a routine by its workflow, repository, and goal, so a second run with the same file changes nothing. A changed routine gets a new version. It prints a count per section and never a secret. | `node services/engine/setup.ts <file>` with `DATABASE_URL`, `CREDENTIAL_KEY`, and `CREDENTIAL_KEY_VERSION` set. The zod schemas in `features/tasks/setup.ts` and `features/credentials/setup.ts` define the file, and `setupFile` in `features/credentials/verify.ts` is an example. `npm run verify -- setup` runs the command against Postgres with made-up logins. | `services/engine/setup.ts`, `features/tasks/setup.ts`, `features/credentials/setup.ts` |
| Stored credentials | Stores each person's GitHub token, Codex login, and Jira login, which is the Jira email and API token joined as `email:token`, sealed with AES-256-GCM. The dashboard's database role can replace a credential but never read one back, and each replacement records who made it and when. The engine opens a credential for the person a run acts as. | No screen yet. `npm run verify -- credentials` runs every behavior against Postgres. | `features/credentials/`, `db/migrations/20260923232000_credential_kinds.sql`, `db/migrations/20260923232100_credentials.sql` |
| Credential checks | The engine checks each stored credential after every replacement, and a Codex login once more inside its 5-minute refresh window. It records each check's state and time on the credential and in `credential_check`. The Codex check runs `codex exec` on `gpt-6-luna` and answers `ack`, and when Codex refreshed the login, the engine seals the new login back over the one it opened. The GitHub check calls `GET /user` and records the token's expiry from the response header. The Jira check calls `GET /rest/api/3/myself` on `JIRA_SITE` and reports `valid` on 200, `invalid` on 401, and `unknown` otherwise. One check runs per credential at a time, a login is refreshed by at most one check, and a check that stopped mid-refresh leaves the login `invalid` with an instruction to store a new one. A Job gets only an access-only copy of a login, checked within the last 6 hours. | `node services/engine/main.ts` with `CREDENTIAL_KEY` and `CREDENTIAL_KEY_VERSION` set, and optionally `CHECKS_EVERY_MS` (60000), `CHECK_LEASE_MS` (300000), `CHECK_TIMEOUT_MS` (120000), and `GITHUB_API_URL`. Without `CREDENTIAL_KEY` the engine runs no checks and says so. `npm run verify -- codex-check` checks an access-only login mounted at `/codex/auth.json`, `npm run verify -- github-check` checks against a local fake or, with `--live`, `GITHUB_TOKEN`, and `npm run verify -- credentials-sim` runs the loop in the simulator. | `features/credentials/`, `db/migrations/20260924120000_credential_checks.sql`, `services/engine/main.ts` |
| Outbox | Performs each external action a task owes, such as a comment, a pull request, or a merge. A state change owes its actions through `enqueue`, which takes only the branded transaction from `shared/transaction.ts`, so a row commits with the state that owes it or not at all. A task with an unsettled row is not ready, so its next step cannot be claimed. A performer claims one row at a time with a lease, in order within each task, drops a row whose task was stopped, looks for the row's marker first when the target cannot catch a duplicate, and checks its lease right before the call, whose deadline is the lease's end less a margin. A failed call keeps its claim until the lease runs out, and each lapse counts as a try. At the cap the row fails and its task waits for a person with the row's last error. Retry owes the failed rows again with their tries reset. A performer can end a row as refused, with the head it named, which drops the rows owed after it. | No screen yet. The engine runs the `outbox` loop once a connector registers an action kind, with `OUTBOX_EVERY_MS` (1000), `OUTBOX_LEASE_MS` (60000), `OUTBOX_MARGIN_MS` (5000), and `OUTBOX_MAX_TRIES` (3). `npm run verify -- outbox-sim` runs seeded performers against Postgres, `--mutant all` proves each guard, and `npm run verify -- outbox-perf` times one engine. | `features/outbox/`, `shared/actions.ts`, `shared/transaction.ts`, `shared/merge-state.ts`, `db/migrations/20260924120100_outbox.sql` |
| Verify environments | Gives each Verify attempt an environment from the Verify provider its repository names, `tests-only` by default, which runs the repository's fast test command in the agent's own workspace, or the checks in its CI config when it has none. It records each start before calling the provider, and the `environments` loop stops the environment of every attempt that ended, lost, or stopped within one interval, and records the stop once no start can still land. The engine refuses to start and names the provider when a repository names one it was not given, and a Verify attempt for such a repository gets a note naming it. | `node services/engine/main.ts` with `DATABASE_URL`, and optionally `ENVIRONMENTS_EVERY_MS` (30000) and `ENVIRONMENT_START_DEADLINE_MS` (600000). A repository row's `verify_provider` and `fast_test_command` choose the environment. `startEnvironment` in `features/environments/lifecycle.ts` is what a Verify step calls. `npm run verify -- environments-live`, `environments-engine`, `environments-sim`, and `environments-perf` run it. | `features/environments/`, `services/engine/main.ts`, `db/migrations/20260924160000_verify_environments.sql` |
| Attempt Jobs | Launches each attempt as a Kubernetes Job from the core's attempt image, or from a repository's own public image that extends it, always named by digest. The Job's per-attempt Secret holds the attempt's keys, the run-as identity's GitHub token, and an access-only Codex login, and no Kubernetes or database credential. The Job clones the repository at the attempt's start commit on `autoworker/<task key>-attempt-<n>` and prints `workspace ready at <sha> on <branch>`. `pushStep` pushes only to that branch, with a lease on its last pushed commit. The sweep deletes the Job and Secret of every finished attempt and of every Job with no attempt row. | `node services/engine/main.ts` with `JOB_IMAGE` set, and optionally `JOB_NAMESPACE` (default), `JOB_SERVICE_ACCOUNT` (autoworker-job), `JOB_DEADLINE_SECONDS` (14400), and `SWEEP_EVERY_MS` (30000). Without `JOB_IMAGE` the engine launches no Jobs and sweeps none, and says so. The launcher is `manifests` and `launch` in `features/jobs/launch.ts`. `npm run verify -- jobs` proves the invariants without a cluster, and `docker compose run --rm live npm run verify -- jobs-live [lane ...]` runs them on kind, with `all` for every lane. | `features/jobs/`, `services/job/`, `shared/codex-login.ts`, `db/migrations/20260924210000_repository_jobs.sql`, `services/engine/main.ts` |
| Agent event bridge | Inside an attempt's Job, the bridge starts `codex app-server` over standard input and output, pins the model `gpt-6-luna`, approval policy `never`, sandbox `danger-full-access`, and reasoning effort `medium` in `thread/start`, so a repository's `.codex/config.toml` changes none of them. It numbers every line the app server writes and posts them to the engine, up to 256 at a time, and resends from the first line the engine has not acknowledged, so an engine outage loses and duplicates nothing. The engine stores each line once and in order, deletes an item's streamed fragments when the item completes, refuses a call with the wrong token, from a second bridge process, with another protocol number, or for an attempt that has ended, and renews the attempt's lease on each call. The engine sends a turn's start, a person's steering message, and a stop back on a command stream the bridge holds open, and records each command as sent, received, or acted on. An attempt finishes only in the transaction that stores its Job's end line. `shared/items.ts` turns stored lines into a transcript of items and turns and reads a turn's final message. | The engine serves it with `node services/engine/main.ts`, on `BRIDGE_PORT` (4520), with optionally `BRIDGE_POLL_MS` (250), `BRIDGE_KEEPALIVE_MS` (5000), and `BRIDGE_BODY_LIMIT_BYTES`. The Job side is `runBridge` in `features/bridge/job.ts`, which the attempt image runs from P3 on. No screen yet. `npm run verify -- bridge-sim` runs the engine and bridge code under faults against Postgres, and `docker compose run --rm live npm run verify -- bridge-live --lane <lane>` runs a real turn for the lanes `outage`, `long-outage`, `steer`, `stop`, `fence`, `planted`, and `wire`. | `features/bridge/`, `shared/items.ts`, `db/migrations/20260924210100_bridge.sql`, `services/engine/main.ts` |
| Jira connector | Finds a routine's tickets in Jira and performs its ticket actions. A routine whose source is `{"kind": "jira-search", "jql": "..."}` searches with `POST /rest/api/3/search/jql` as its run-as person, or else its creator, follows the page token to the last page, and records one task per ticket key with the ticket's summary and assignee account. `ticket.comment` posts an Atlassian-document comment that carries the row's marker as the comment property `autoworker`, after reading every page of the ticket's comments, so a retried row that finds its marker on a comment its identity wrote posts nothing. With `linkPullRequest` it appends the URL from the task's done `pr.open-draft` row. `ticket.transition` reads the ticket's status each time: a ticket already in the target status is done, a ticket in any status other than the expected `from` fails the row and names the status it found, and otherwise it moves the ticket by the name of the target status. A routine version keeps the optional `jira_start_status` and `jira_end_status`. The assignee read returns a ticket's current assignee account. | `node services/engine/main.ts` with `JIRA_SITE` and `CREDENTIAL_KEY` set, and optionally `JIRA_TIMEOUT_MS` (30000). A person's Jira login comes from setup's `logins.jira`. `npm run verify -- jira` runs the source and performers against a local fake Jira. `docker compose run --rm -e JIRA_PROJECT=<key> live npm run verify -- jira-live --lane <lane>` runs a lane against the sandbox Jira with the real engine, where the lane is `flow`, `twice`, `assignee`, `search-identity`, `restart`, `no-marker`, `same-status`, `check`, `pages`, or `perf`. | `features/jira/`, `features/credentials/jira-check.ts`, `features/credentials/jira-login.ts`, `shared/jira-login.ts`, `shared/routine-source.ts`, `db/migrations/20260924220100_jira_kind.sql`, `db/migrations/20260924220101_jira.sql`, `services/engine/main.ts` |
| GitHub pull requests | Opens a draft pull request from a task's branch, writes Verify's evidence into its body and marks it ready, updates a branch that is behind, merges at the head Land read, or joins the merge queue at that head when the base branch uses one. It creates or fast-forwards a task's branch only from the commit its row names, and deletes branches. A repeat that GitHub refuses as a duplicate counts as done, a merge whose head moved is refused and names the head, and an ejection after the row was owed is the merge row's outcome. It reads each pull request's merge state from GitHub under the repository's own rules into one value for Land. A queued pull request reads as queued before anything else, a check not yet reported reads as waiting, a failed check the repository lists as ignorable does not make it red, and changes requested by a reviewer the repository ignores never reach Land. The client can never submit a review, so AutoWorker never approves a pull request. | The outbox loop performs `pr.open-draft`, `pr.mark-ready`, `pr.update-branch`, `pr.merge`, `branch.advance`, and `branch.delete` as the identity each row acts for, with `GITHUB_API_URL`. A repository row's `ignorable_checks`, `ignored_reviewers`, and `draft_leaves` (`when-green` by default, or `at-once`) set its rules. `mergeStateReader` in `features/github/merge-state.ts` is what Land reads. `npm run verify -- github-sim` runs the real client against a seeded fake GitHub, `--mutant all` proves each guard, and `docker compose run --rm live npm run verify -- github-live --open <number>` reads real pull requests and times each read. | `features/github/`, `services/engine/main.ts`, `db/migrations/20260924180000_repository_review_settings.sql` |
