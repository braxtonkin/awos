# Core behaviors

The whole specification. It describes the system to build and nothing that exists today.

AutoWorker carries a ticket to a merged change without a person driving it. A person decides what should happen and reviews the result, and everything between those two points is the system's job. It is built for trust rather than throughput, because a team can only run as many agents as it can verify. That means every part of it can be checked on its own, and a person can always see what it is doing.

It is made of five things and nothing else. **Routines** start work on a schedule, and a person who does not own the system can add a new one. **Access to the product** means work happens against the real repository and the real cluster, and ends in a merged change rather than a proposal. **Observability** means anyone can see what is happening now, what happened last month, and what an agent actually did. **Credentials** mean every action runs under a named human's authority and stays traceable to them afterward. An **execution environment** gives work the tools and isolation it needs, so two units of work cannot interfere with each other.

A unit of work is one ticket, and it moves through four stages. Specify, implement, verify, and land. Each stage takes a stated input, produces a stated output, and ends in a verdict. Each one runs on its own, which is the point: a failure costs one stage instead of the whole ticket, a stage can be tested without the others, and stages can be recombined to work something large in parallel. The verify stage produces evidence, meaning whatever artifact shows the check actually happened, and that evidence attaches to the work and outlives the run that made it.

Failure is the normal case rather than the exception. A stage that fails keeps every earlier stage's output and can be retried alone. A restart resumes in-flight work without repeating an external action that already succeeded, because performing any external action twice is the same as performing it once. Two workers cannot claim the same ticket, and the second is refused outright rather than prevented by checking first. Work that dies is noticed within one scheduling interval and released. Work that is genuinely stuck moves into a waiting state a person can find by asking, and stops consuming capacity. At any time a person can stop a unit, retry one stage, or reassign its operator.

Everything the system knows about work lives in one authoritative record in Postgres. Ownership, stage, attempt, and evidence are facts there. Branches, pull requests, tickets, and cluster resources are observations that get recorded and reconciled, and none of them is ever a second owner of a unit of work. Invariants belong to the schema rather than to code that checks and then acts, so a unit has at most one live attempt because the store refuses a second, and ownership expires on a lease so nothing stays owned by a process that has died. An external action is committed alongside the state that owes it, and a separate pass performs it. There is no fallback to deriving state from files, because a fallback becomes the real path and then both have to be maintained.

Routines are data, not code. No part of the execution machinery contains the name of any routine or step, and a test enforces that rather than a reviewer. Each routine declares its own schedule, and declares how far it may go, whether that is reporting what it found, proposing a change, or making the change. A routine that stops running is noticed, because one assumed to be working and quietly dead is worse than one that was never built.

The acceptance test for all of it is that **AutoWorker delivers its own changes.** If it cannot take a ticket against itself and land the result, it is not finished.

Four things are deliberately undecided. Exactly where the four stage boundaries fall, whether a unit of work runs as a supervised subprocess or its own scheduled job, how much test coverage a product needs before a routine may change it, and how long history is kept.
